The one idea to carry up every floor

Training is a big, parallel job you run once. Inference is a stream of small, sequential jobs you run forever, and generating each token mostly waits on memory, not on maths. Almost every technique in this handbook either moves fewer bytes per token, or shares each byte moved across more tokens.

Floor 1 · Foundations

The inference workload

What happens when a model answers, how to measure it, and the trade-off that shapes every decision after.

Chapter 1.1

Why inference engineering

“

Training a model is a large bill you pay once. Inference is a bill you pay every day, and it grows with users, with longer answers, with reasoning tokens and with agents that call the model dozens of times per task.

Picture it: where the money goes over a model's life

Illustrative shape, not real figures. For a popular model, cumulative serving cost overtakes the one-off training cost.

Different workloads, different goals
ChatA person is waiting. First token fast, then steady streaming.
Code completionShort outputs, very tight latency; every keystroke may fire a request.
Batch jobsSummarise a million documents overnight. Only throughput and cost matter.
AgentsMany sequential calls with long, growing contexts that share prefixes.
Evals and RL rolloutsThousands of samples per prompt; throughput-bound, and now a large share of training compute.
ReasoningThousands of hidden thinking tokens per answer: decode-heavy and expensive.

Name the workload first

  • "Make inference faster" means different things: lower time to first token, faster streaming, or more tokens per GPU-hour. They often pull against each other.
  • Write down the workload shape (prompt length, output length, concurrency, latency target) before choosing any technique in this handbook.
Chapter 1.2

Prefill and decode

“

Every request has two phases. Prefill reads the whole prompt at once, in parallel, and is limited by compute. Decode then writes one token at a time, and each step must reread the model's weights and the cached past, so it is limited by memory bandwidth.

Picture it: step through one request
  1. A request arrives with a prompt of several tokens (real prompts: hundreds to hundreds of thousands).
  2. Prefill: every prompt token goes through the model at once. Big matrix multiplications keep the GPU's maths units busy: compute-bound.
  3. Prefill stores each token's attention keys and values: the KV cache. Without it, every later step would recompute the whole history.
  4. The first output token appears. The time until now is time to first token.
  5. Decode: one token per step. Each step does little maths but must read every weight and the whole KV cache from memory. The GPU mostly waits on memory: memory-bound.
PrefillDecode
WorkAll prompt tokens in parallelOne token per sequence per step
BottleneckCompute (FLOPs)Memory bandwidth (bytes)
SetsTime to first tokenTime per output token
Grows withPrompt lengthOutput length, concurrency, context
 
def generate(model, prompt_ids, max_new=200):
    # prefill: one parallel pass over the whole prompt, filling the KV cache
    logits, kv_cache = model(prompt_ids, kv_cache=None)
    out = [sample(logits[-1])]
    # decode: one token per step, reusing (and growing) the cache
    for _ in range(max_new - 1):
        logits, kv_cache = model([out[-1]], kv_cache=kv_cache)
        out.append(sample(logits[-1]))
        if out[-1] == EOS:
            break
    return out

Two phases, two tuning problems

  • Long prompts (RAG, agents, documents) make prefill dominate: fix with prefix caching and chunked prefill (Floor 6).
  • Long answers and many users make decode dominate: fix with batching, smaller KV caches, quantisation and speculation (Floors 3–6).
Chapter 1.3

The metrics that matter

“

Users feel two things: how long before text appears, and how fast it then streams. Operators care about how many tokens each GPU produces. Goodput joins them: requests per second served within the latency targets.

Write SLOs per workload

  • Example: chat p99 TTFT under 1.5 s and p99 TPOT under 50 ms; batch jobs: cost per million tokens only.
  • Measure TTFT from the client, including queueing; engine logs often exclude time spent waiting.
Chapter 1.4

Latency vs throughput

“

Batching many users into each decode step shares the cost of reading the weights, so total throughput soars. But each step reads more cache and does more work, so every individual user waits a little longer, and memory caps how big the batch can get.

Try it: an 8B model on one H100

Ideal model, after CS336's lecture: step time = the larger of (weights + KV cache bytes) ÷ 3.35 TB/s and 2 × params × batch ÷ 989 TFLOP/s. BF16 weights (16 GB), 128 KB of KV cache per token. Real engines reach perhaps half to three quarters of these numbers.

Pick a point on the curve on purpose

  • Latency-critical products cap the batch (or the concurrency per replica) to protect TPOT; batch products push it to the memory limit.
  • Anything that shrinks the KV cache (Floor 3) moves the memory wall right, which is where most throughput gains come from.
Chapter 1.5

Counting FLOPs and bytes

“

Two back-of-envelope rules get you surprisingly far. A forward pass costs about 2 FLOPs per parameter per token. And a decode step can't finish faster than the time it takes to read every weight byte from memory.

Try it: size a model
def back_of_envelope(params, bytes_per_param, hbm_bytes, hbm_bw):
    weights = params * bytes_per_param                  # bytes to store and to read per step
    gpus_needed = -(-weights // (0.8 * hbm_bytes))      # leave ~20% for KV cache etc.
    flops_per_token = 2 * params                        # one multiply + one add per weight
    best_step_s = weights / (hbm_bw * gpus_needed)      # read every weight once per step
    return weights / 1e9, gpus_needed, flops_per_token, 1 / best_step_s

print(back_of_envelope(70e9, 2, 80e9, 3.35e12))   # ~140 GB, 3 GPUs, 1.4e11 FLOPs, ~72 tok/s ceiling

Do the arithmetic before the benchmark

  • If a vendor claims a single-stream speed above the bandwidth ceiling, they're using speculation, quantisation or a smaller model; ask which.
  • These ceilings ignore the KV cache and overheads, so they're upper bounds. Real systems land below them.

Floor 2 · Foundations

Hardware and the roofline

Where the time goes inside a GPU, and the one diagram that tells you which optimisation will help.

Chapter 2.1

Inside a GPU

“

A GPU is thousands of very fast maths units sitting next to a small amount of very fast memory, connected to a much larger, slower memory (HBM). The maths units can almost always work faster than HBM can feed them, so keeping them fed is the whole game.

Picture it: the memory hierarchy of an H100
SMsStreaming multiprocessors: the GPU's cores. An H100 SXM has 132, each with tensor cores for matrix maths.
Tensor coresSpecial units for matrix multiply in low precision (BF16, FP8, FP4). Where the headline TFLOPs come from.
HBMHigh-bandwidth memory stacked beside the chip. Large and fast by any normal standard, but slow relative to the maths.
KernelsPrograms launched on the GPU. Each kernel reads inputs from HBM and writes results back: every round trip costs time.
More TFLOPs means faster LLM responses.
→
For decode, memory bandwidth and capacity usually matter more than TFLOPs. The H200 has the same compute as the H100 but more, faster memory, and serves LLMs noticeably faster.

Read spec sheets carefully

  • Vendors often quote TFLOPs with 2:4 sparsity, which doubles the number; LLMs rarely use it. Compare dense figures.
  • For serving, rank chips by memory capacity, memory bandwidth, then low-precision dense FLOPs, then interconnect.
Chapter 2.2

Arithmetic intensity and the roofline

“

Arithmetic intensity is FLOPs done per byte moved. Below the chip's ridge point, a job is limited by memory bandwidth; above it, by compute. The roofline plot shows which wall you're under, and therefore which optimisations can help.

Try it: the roofline

Dense peak figures. Intensity for a weight-matrix multiply with batch B in BF16 is about B FLOPs per byte; lower precision doubles or quadruples FLOPs per byte read.

Under the slope (memory-bound)Fix by moving fewer bytes: smaller weights (quantise), smaller KV cache, fusing kernels, or batching more work per byte.
Under the flat roof (compute-bound)Fix by doing fewer FLOPs or faster ones: lower-precision tensor cores, skipping work (prefix caching), better kernels.

Profile before you optimise

  • An optimisation that cuts FLOPs does nothing for a memory-bound decode step, and vice versa. Place the operation on the roofline first.
  • Nsight Systems and Nsight Compute (or the PyTorch profiler) show achieved bandwidth and FLOPs per kernel; compare them with the roofline to see headroom.
Chapter 2.3

Why decode is memory-bound

“

Multiplying B tokens by a weight matrix does about B FLOPs for every byte of weight read. An H100 needs roughly 295 FLOPs per byte to keep its maths busy in BF16, so decode with fewer than a few hundred sequences in the batch leaves compute idle. Attention during decode is worse: each sequence has its own cache, so batching doesn't help at all.

Picture it: the matrix multiply that dominates
Try it: compute-bound or memory-bound (H100, BF16)?
def matmul_intensity(B, D, F, bytes_per=2):
    flops = 2 * B * D * F
    bytes_moved = bytes_per * (B * D + D * F + B * F)   # read X and W, write Y
    return flops / bytes_moved

ridge_h100_bf16 = 989e12 / 3.35e12                       # ≈ 295 FLOPs per byte
for B in (1, 16, 64, 256, 1024):
    i = matmul_intensity(B, 8192, 28672)
    print(B, round(i), "compute-bound" if i > ridge_h100_bf16 else "memory-bound")

This one fact explains most of the handbook

  • Batching (Floor 6) raises intensity for the weight multiplies. Shrinking the KV cache (Floor 3) cuts the bytes attention reads. Quantisation (Floor 4) cuts bytes everywhere. Speculation (Floor 5) checks several tokens per weight read.
  • Prefill is already compute-bound, so these tricks mostly help decode; prefill improves with faster maths and caching repeated prompts.

Memory is the new budget line

  • Moving from H100 to H200 gives no extra FLOPs but about 1.4× bandwidth and 1.8× memory, which translates almost directly into faster decode and bigger batches.
  • Blackwell's FP4 doubles both FLOPs and effective bandwidth again, but only if your model quantises to FP4 without losing quality (Floor 4).
Chapter 2.5

Beyond NVIDIA

“

Other accelerators make different bets on the same trade-off. Some add far more HBM per chip, some keep weights in on-chip SRAM for blistering single-stream speed, and some optimise cost per token inside one cloud. The roofline still applies to all of them.

AMD Instinct (MI300X onwards)Large HBM per GPU (MI300X: 192 GB at 5.3 TB/s), so big models fit on fewer chips. Software via ROCm; vLLM and SGLang support it.
Google TPUSystolic-array chips connected in large pods; programmed through JAX/XLA. Strong at high-throughput serving inside Google Cloud.
AWS Trainium / InferentiaAWS's own chips through the Neuron SDK; priced to cut cost per token for workloads that port cleanly.
SRAM-first designs (Groq, Cerebras)Keep weights in on-chip SRAM across many chips or a whole wafer: extremely fast tokens per second per user, with different cost and capacity trade-offs.

Portability is the hidden cost

  • Check that your serving engine, quantisation formats and kernels (attention, MoE) are mature on the target chip before comparing price per hour.
  • Benchmark your own model and workload; vendor charts use their best case.

Floor 3 · Memory & model

Memory and the KV cache

Weights are fixed; the KV cache grows with every user and every token. Managing it is half the job.

Chapter 3.1

Where the memory goes

“

GPU memory holds three things: the model's weights (fixed), the KV cache (grows with every user and every token), and working space for activations and the runtime. Whatever the weights leave over decides how many users you can serve at once.

Try it: fill a GPU
1

10% of memory reserved for activations, CUDA graphs and fragmentation; engines expose this as a "GPU memory utilisation" setting.

Concurrency is a memory number

  • The maximum number of simultaneous users per replica is roughly (free memory after weights) ÷ (KV per user). Every chapter on this floor is about raising that number.
  • Long-context products need dramatically more memory per user; price and capacity-plan them separately.
Chapter 3.2

The KV cache

“

For every token, every layer stores a key vector and a value vector for each KV head. That's 2 × layers × KV heads × head size × bytes, per token, for as long as the conversation lasts.

Picture it: one token's cache entry
Try it: KV size for real models
def kv_bytes_per_token(layers, kv_heads, head_dim, bytes_per=2):
    return 2 * layers * kv_heads * head_dim * bytes_per   # 2 = one key + one value

llama3_8b  = kv_bytes_per_token(32, 8, 128)    # 131,072 B = 128 KB
llama3_70b = kv_bytes_per_token(80, 8, 128)    # 327,680 B = 320 KB
llama2_13b = kv_bytes_per_token(40, 40, 128)   # 819,200 B = 800 KB (no GQA)
print(llama3_70b * 128_000 / 1e9, "GB for one 128k-token conversation")   # ~42 GB
The model's size decides how much memory serving needs.
→
At long contexts and high concurrency, the KV cache can be several times larger than the weights.

Check the config, not the parameter count

  • Two models of the same size can differ several-fold in KV per token because of KV heads and attention design. Read config.json before sizing hardware.
Chapter 3.3

Sharing heads: MQA, GQA, MLA

“

Standard attention keeps separate keys and values for every query head. Grouped-query attention lets several query heads share one KV head; multi-query shares one across all; multi-head latent attention stores a small compressed vector and expands it when needed.

Try it: switch the attention design

Built in at training time

  • These are architecture choices made before pretraining; you choose them by choosing the model. Most current open models use GQA; DeepSeek's models use MLA.
  • Existing MHA models can be converted (for example "uptraining" to GQA), but that's a retraining project, not a serving flag.
Chapter 3.4

Windows, hybrids and state-space models

“

Full attention keeps every past token, so the cache grows forever. Sliding-window layers keep only recent tokens; hybrid models mix a few full-attention layers with many local or linear ones; state-space models replace the cache with a fixed-size state.

Try it: cache size as conversations grow
━ full attention━ 1 full : 5 window layers━ all window━ state-space

Total cache relative to a full-attention model at 128k tokens. The hybrid ratio follows designs such as character.ai's, cited in CS336; many recent open models mix local and global layers.

Sliding windowEach layer sees only the last W tokens; information from further back flows indirectly through stacked layers.
Hybrid local/globalMost layers local, every few layers global: most of the saving, much less quality loss.
State-space and linear attentionMamba-style layers keep an O(1) state instead of an O(T) cache. Hybrids (e.g. Jamba) interleave them with attention.

Ask how a model "supports" long context

  • A 1M-token context window on a hybrid model and on a full-attention model have very different memory bills and recall behaviour. Test recall on your own long documents.
Chapter 3.5

Quantising and offloading the cache

“

Two serving-side levers need no retraining. Store the cache in FP8 to halve it. And move caches you'll need again (earlier turns, shared documents) to CPU memory or SSD instead of throwing them away: reloading is usually far faster than recomputing.

Try it: reload or recompute?

Llama-3-8B, 128 KB per token. Recompute assumes 10,000 prompt tokens per second of prefill. Tier speeds are typical effective rates: CPU over PCIe 5 ~50 GB/s, Grace-Hopper/Blackwell chip-to-chip ~450 GB/s, local NVMe ~5 GB/s, network storage ~2 GB/s.

FP8 KV cacheA common engine setting: about half the memory, small accuracy cost; check on long-context evals.
Tiered KV storesLMCache, SGLang HiCache and Dynamo's KV block manager keep caches in CPU memory, SSD or shared storage and reload on reuse.
PreemptionWhen memory runs out mid-flight, engines evict a request's cache: swap it out, or drop it and recompute later.

Agents and multi-turn chat benefit most

  • Agent loops resend a long, growing context every step. Keeping that cache warm (on GPU or a nearby tier) can cut TTFT by an order of magnitude.
Chapter 3.6

The cost of long context

“

Long prompts cost twice. The KV cache grows linearly, eating concurrency. And prefill attention grows with the square of the prompt length, so past some length attention dominates the FLOPs and time to first token climbs steeply.

Try it: where prefill FLOPs go (8B model)
0of FLOPs in attention
0s prefill at 50% of H100 peak

Weights: 2 × 8B FLOPs per token. Causal attention: about 2 × layers × width × S² in total (QKᵀ and AV), using 32 layers and width 4,096.

Retrieve, don't stuff

  • Sending only relevant passages (RAG), caching shared prefixes, and summarising old turns are usually cheaper than buying context length.
  • Expect providers to price long-context tokens higher; this is why.

Cheaper tokens from the model

Make every token cost less by changing the numbers, the architecture or the model itself, and prove quality held.

Chapter 4.1

Number formats

“

Every weight is a number stored in some number of bits. Fewer bits means fewer bytes to move per token, so decode gets faster and more fits in memory. The catch is rounding error, and one large outlier can wreck the rounding for everything that shares its scale.

Picture it: the bits

Why block scaling won

  • Modern 4-bit formats give each small block its own scale: MXFP4 uses blocks of 32 with a power-of-two scale; NVIDIA's NVFP4 uses blocks of 16 with an FP8 scale. An outlier then only hurts its own block.
  • Blackwell GPUs run FP4 matmuls natively; Hopper has FP8 but not FP4.
Chapter 4.2

Quantisation methods

“

Weight-only quantisation shrinks what decode must read, so it speeds up small-batch serving. Quantising weights and activations lets the tensor cores do cheaper maths too, which is what speeds up prefill and big batches.

Try it: what speeds up, and when

MethodWhat's low-precisionIdeaTypical use
GPTQWeights (INT4/INT3)Quantise column by column, adjusting the rest to cancel the error, using a small calibration setSmall-batch, memory-limited serving

4-bit weights make everything 4× faster.
→
They mainly speed up memory-bound decode. At large batch the GPU must dequantise before multiplying; CS336 notes LLM.int8() ran 15–23% slower than BF16.

Start with FP8

  • On Hopper or Blackwell, FP8 weights, activations and KV cache are the low-risk first step. Go to 4-bit when memory, not quality, is the constraint, and re-run your evals.
  • Use checkpoints the model maker published in low precision where they exist; they were often quantisation-aware trained.
Chapter 4.3

Mixture of experts at inference

“

A mixture-of-experts model has many feed-forward "experts" per layer, and a router sends each token to only a few. Compute per token follows the active parameters, but memory must hold all of them, and at real batch sizes almost every expert gets read each step.

Try it: how many experts does a batch touch?

Assumes the router spreads tokens evenly at random: touched share = 1 − (1 − k/E)B per layer. Real routing is uneven, which makes the hottest experts busier.

Good newsFLOPs per token follow active parameters: DeepSeek-V3 has 671B parameters but uses about 37B per token.
Bad newsAll 671B must sit in memory, and each expert sees only a few tokens per step, so expert matmuls have low arithmetic intensity.
The fixHuge batches spread across many GPUs, one group of experts per GPU: expert parallelism (Floor 7).

MoE is cheap at scale, awkward when small

  • For a high-traffic API, MoE gives big-model quality at small-model FLOPs. For a single low-traffic replica you pay to hold every expert and get little batching benefit.
Chapter 4.4

Distillation and pruning

“

Instead of making the same model cheaper, make a smaller model that behaves like it. Pruning cuts layers, heads or neurons that matter least; distillation then trains the smaller model to copy the big one's outputs.

Picture it: prune, then heal
Start bigA strong model you already have.
Score partsRun calibration data (CS336 cites ~1,024 samples) and measure each part's importance.
CutDrop the least important layers (depth) or neurons and heads (width).
DistilTrain the small model to match the teacher's output probabilities. Quality mostly returns.
import torch.nn.functional as F

def distill_loss(student_logits, teacher_logits, labels, T=2.0, alpha=0.5):
    soft = F.kl_div(F.log_softmax(student_logits / T, -1),
                    F.softmax(teacher_logits / T, -1), reduction="batchmean") * T * T
    hard = F.cross_entropy(student_logits, labels)
    return alpha * soft + (1 - alpha) * hard     # copy the teacher, still learn the data
Logit distillationMatch the teacher's full probability distribution: rich signal, needs the teacher's weights.
Data distillationFine-tune on answers the teacher wrote: works through an API, the common route for task-specific small models.
SparsityGPUs can skip zeros in a 2:4 pattern, but quality loss and modest real speedups keep it rare for LLMs.

Narrow tasks distil best

  • A small model distilled for one task (classification, extraction, routing) can match a frontier model on that task at a fraction of the cost. Check the model's licence allows training on its outputs.
Chapter 4.5

The smallest model that passes

“

Try it: set the quality bar

Floor 5 · Speed

Faster decoding

Generate more tokens per expensive step, and make each step's kernels waste less time.

Chapter 5.1

Speculative decoding

“

Decode wastes the GPU's maths because each step reads all the weights to make one token. So let a small, fast draft model guess several tokens, then have the big model check them all in one pass. Every correct guess is a token you got almost free, and the output is exactly what the big model would have produced.

Picture it: guess, then verify
  1. Normal decode: the big model makes one token per pass, each pass rereading every weight.
  2. A small draft model (say 1B for an 8B target, or 8B for a 70B target, as in CS336) guesses the next k tokens quickly.
  3. The target runs once over all the guesses. That costs about the same as one normal decode step, because decode was memory-bound and the extra tokens ride along.
  4. Accept guesses up to the first mismatch, then take the target's own token there. A rejection-sampling rule makes the output distribution identical to the target's: lossless.
Try it: tune the draft

Leviathan et al.: tokens per target pass = (1 − αk+1) ÷ (1 − α); speedup = that ÷ (1 + k·c). Assumes the verify pass costs the same as a normal step, which holds while decode is memory-bound.

Speculative decoding always helps.
→
It spends spare compute. At large batch sizes the GPU is already compute-bound, verify passes stop being free, and the gain shrinks or reverses.

Measure acceptance on your traffic

  • Acceptance depends on the text: code and structured output are predictable, creative writing less so. Tune k per workload, and turn speculation down when the batch is large.
Chapter 5.2

Draft-free speculation

“

A separate draft model costs memory and needs the same tokeniser. Newer methods bolt small prediction heads onto the target itself, or simply copy likely continuations from the prompt.

Picture it: a tree of guesses
MedusaExtra heads on the target's last layer each predict a token further ahead; candidates form a tree.
EAGLE (1–3)A one-layer drafter reads the target's internal features, so its guesses are much better than a separate small model's.
MTPMulti-token prediction modules trained with the model. DeepSeek-V3 reported 85–90% acceptance for the extra token, about 1.8× tokens per second.
N-gram / prompt lookupCopy the continuation from text already in the prompt. Free, and excellent for code edits, RAG answers and rewrites.
Try it: which speculation fits?

Use what ships with the model

  • If the model maker published MTP or EAGLE weights, start there; vLLM, SGLang and TensorRT-LLM support them. Add n-gram lookup for edit-heavy workloads.
Chapter 5.3

Sampling and structured output

“

After each forward pass the model outputs a score for every token in its vocabulary. Sampling settings reshape those scores before picking one. Constrained decoding goes further: it masks out every token that would break a JSON schema or grammar, so the output is valid by construction.

Try it: temperature and top-p

"The soup needs more …"

Grey tokens fall outside top-p and can't be picked. Temperature near 0 is effectively greedy: always the top token.

Picture it: a grammar mask
Free decoding{"city": "Paris", "temp": twentyInvalid JSON one time in a few hundred; your parser fails at 3 a.m.
Constrained decoding{"city": "Paris", "temp": 2 ← only digits allowed hereAt each step, tokens the schema forbids get probability zero.

Inference-side details that bite

  • Grammar engines (XGrammar, llguidance, Outlines) precompute masks so the overhead is tiny; slow ones can cut throughput noticeably. Benchmark with your schemas.
  • Outputs can differ run to run even at temperature 0, because batch size changes the order of floating-point sums. Batch-invariant kernels fix this at some speed cost; use them where you need reproducibility.
Chapter 5.4

Reasoning models think before answering, often for thousands of tokens. That moves the cost of a request from the prompt to the output: decode speed now decides both latency and bill.

Try it: where the time goes

Price and plan by output tokens

  • Capacity plans built on chat-style output lengths fall over when a reasoning model writes 10× more. Measure output-length distributions per feature, and cap thinking where quality allows.
Chapter 5.5

Kernels and fusion

“

A model step is hundreds of small GPU programs called kernels. Each one reads its inputs from HBM and writes results back. Fusing kernels removes those round trips; FlashAttention never writes the full attention matrix; CUDA graphs remove the CPU cost of launching them all.

Picture it: unfused vs fused
Try it: CPU launch overhead in decode

Batch-1 decode on H100s; ~5 µs CPU cost per launch when the GPU finishes kernels faster than the CPU can issue them. A graph replays the whole step with one launch.

FlashAttentionTiles attention so scores stay in on-chip SRAM: memory O(S) not O(S²), and much faster prefill.
FlashDecodingAt batch 1 there's too little parallel work; split the long KV cache into chunks across SMs and combine.
torch.compile, TritonGenerate fused kernels from Python; engines ship hand-tuned ones for hot paths.

Engines do this for you

  • You rarely write kernels to serve a standard model. You do pick an engine and version whose kernels suit your GPU, precision and model architecture; that choice can be worth 2× on its own.

The serving engine

Batching, paging and caching: the systems ideas that turn a model into a high-throughput service.

Chapter 6.1

Continuous batching

“

Requests finish at different times. A static batch waits for its longest request while finished slots sit idle. Continuous batching (Orca's iteration-level scheduling) re-forms the batch at every decode step: a finished request leaves and a waiting one joins straight away.

Try it: four slots, twelve requests
0decode steps to finish all
0of slot-steps doing useful work

Each coloured bar is one request; numbers are its output length. Grey is a slot doing nothing.

Why this matters to you

  • Every modern engine does this. The knobs you tune are the maximum running requests and the per-step token budget; set them from memory and latency targets, not by trial.
  • Orca's other idea, selective batching: matmuls run batched across requests, while attention runs per request because each has its own cache length.
Chapter 6.2

PagedAttention

“

Early servers reserved one contiguous chunk of memory per request, sized for the longest possible output. Most of it sat empty. vLLM's PagedAttention stores the cache in small fixed-size blocks anywhere in memory, tracked by a block table, just as an operating system pages virtual memory.

Picture it: logical blocks, physical pages
Try it: reserved vs paged

Same 64 requests with actual lengths of 300–2,000 tokens; 16-token blocks. The vLLM paper found earlier systems used only about 20–38% of cache memory for real tokens.

More users per GPULess waste means bigger batches, which is where vLLM's reported 2–4× throughput came from.
Sharing for freeParallel samples from one prompt point at the same prompt blocks; copy-on-write only when they diverge.

The setting you'll touch

  • "GPU memory utilisation" decides how much of the card becomes the block pool after weights load. Too high risks out-of-memory on activation spikes; too low wastes users.
Chapter 6.3

Prefix caching

“

Many requests start with the same tokens: a system prompt, tool definitions, a shared document, earlier turns of the chat. If their KV blocks are kept and looked up by content, those tokens never need prefilling again.

Picture it: a radix tree of prompts
Try it: what a cache hit saves
0of prefill compute saved
0ms TTFT on a hit
0ms TTFT on a miss

Prefill at 10,000 tokens/s. SGLang's RadixAttention and vLLM's automatic prefix caching both do this.

Order prompts for the cache

  • Put what's stable first (instructions, tools, reference documents) and what changes last. A timestamp at the top of a system prompt breaks every hit.
  • Hosted APIs pass this on as discounted "cached input" pricing; self-hosted, it shows up as lower TTFT and more capacity. Route returning users to the replica that holds their cache (Floor 7).
Chapter 6.4

Chunked prefill and scheduling

“

When a long prompt arrives, prefilling it in one go stalls every user who's mid-answer: their next token waits for the whole prefill. Chunked prefill (Sarathi-Serve) splits the prompt into pieces and mixes each piece into normal decode steps.

Try it: a 16k-token prompt arrives
0ms worst gap between tokens
0ms TTFT for the new prompt

8B model on an H100 serving 32 users mid-answer: a decode step takes ~20 ms; prefill runs at ~15,000 tokens/s (about half of peak FLOPs).

Token budgetEach step processes at most N tokens (decode tokens first, then prefill chunks): the main latency knob.
PrioritiesInteractive requests ahead of batch jobs; short prompts ahead of huge ones.
PreemptionWhen memory runs out, pause the newest requests and swap or recompute their caches later.

The trade-off is explicit

  • Smaller chunks protect everyone's TPOT but make the new prompt's TTFT longer. Pick the budget from your latency targets for both, or split the phases onto different GPUs (Floor 7).
Chapter 6.5

Inside an engine

“

An inference engine is a loop. Each iteration, the scheduler picks which requests and tokens run, the cache manager finds them blocks, the model runner does one forward pass, and the sampler emits a token per request. Everything on this floor lives in that loop.

Picture it: one engine step
  1. A request arrives over an OpenAI-compatible API and is tokenised.
  2. Every iteration, the scheduler chooses running requests within the token budget: decode tokens, prefill chunks, maybe speculative guesses.
  3. The cache manager allocates blocks, finds prefix-cache hits and preempts if memory runs short.
  4. The model runner executes one forward pass for the whole batch with fused kernels, often replayed from a CUDA graph.
  5. The sampler turns logits into tokens, applying temperature, top-p and any grammar mask.
  6. New tokens stream back to clients; finished requests free their blocks; the loop goes round again.

Distributed inference

When one GPU isn't enough: splitting models, experts and phases across many, and routing work between them.

Chapter 7.1

Why go multi-GPU

“

There are three different reasons, and each has a different answer. If the model doesn't fit, split it. If one user's tokens are too slow, split it so more memory bandwidth works on each token. If you need more total throughput, add copies (replicas), which is simpler and scales almost perfectly.

Try it: how many GPUs to fit?
Doesn't fitTensor parallelism inside a server; pipeline parallelism across servers; expert parallelism for MoE.
Too slow per userTensor parallelism: each GPU reads 1/n of the weights per token.
Not enough throughputReplicas behind a load balancer (data parallelism).

Smallest split that meets the latency target, then replicate

  • Splitting more than you need adds communication and lowers throughput per GPU. Find the smallest parallel group that fits the model and hits TPOT, then scale out with copies of that group.
Chapter 7.2

Tensor parallelism

“

Split every weight matrix across n GPUs. Each GPU multiplies its slice, then they combine partial results with an all-reduce, twice per layer. Each token now reads only 1/n of the weights per GPU, so it gets faster, until communication time dominates.

Picture it: one layer on four GPUs
Try it: TPOT as you add GPUs (70B, FP8, H100, batch 1)

Weight time = 70 GB ÷ (n × 3.35 TB/s). Communication = 160 small all-reduces per token at ~8 µs each over NVLink, ~30 µs over PCIe. Dashed line: ideal scaling with free communication. Illustrative; measured values depend on the engine and batch.

8 GPUs make each token 8× faster.
→
Communication is a fixed cost per layer. Gains flatten, and across servers (slower links) TP usually stops paying.

Keep TP inside the NVLink domain

  • TP 2, 4 or 8 within one server is standard. Rack-scale systems (GB200 NVL72) extend NVLink to 72 GPUs, which is why they matter for very large models.
Chapter 7.3

Pipeline parallelism

“

Give each GPU (or server) a consecutive slice of layers, and pass activations along like an assembly line. Only small activations cross the link, so it works over slower networks. But one token still visits every stage in turn: it fits bigger models, it doesn't make a token faster.

Try it: stages and micro-batches

Each coloured cell is one micro-batch on one stage. Idle (grey) share = (S − 1) ÷ (M + S − 1) for one pass through the pipe.

Typical use

  • Models too large for one 8-GPU server, such as a 405B model in BF16, run as TP 8 inside each server and PP 2 across two. Keep enough requests in flight to fill the pipe.
Chapter 7.4

Expert parallelism

“

For mixture-of-experts models, place different experts on different GPUs. Each MoE layer sends every token to the GPUs holding its chosen experts (all-to-all), computes, and sends results back. Spread over enough GPUs, each expert finally sees enough tokens per step to use its compute.

Try it: DeepSeek-V3 (FP8) across a cluster
0GB of expert weights per GPU
0tokens per expert per step
0of FP8 ridge (~590)

256 routed experts, 8 per token, ~656 GB of expert weights in FP8; attention and shared parts replicated. DeepSeek reported prefill units of 32 GPUs and decode units of 320.

All-to-allDispatch and combine every MoE layer; libraries such as DeepEP overlap it with compute.
Hot expertsRouting is uneven; engines copy busy experts to more GPUs (EPLB) to balance load.
AttentionUsually data-parallel: each GPU runs attention for its own requests.

Wide EP is for big fleets

  • The economics of large MoE models depend on huge, well-balanced batches across dozens of GPUs. Below that scale, a smaller dense model or a hosted API is often cheaper.
Chapter 7.5

Disaggregated prefill and decode

“

Prefill is compute-bound and bursty; decode is memory-bound and steady. On the same GPUs they interfere. Disaggregation runs them on separate pools, each sized and configured for its phase, and moves the KV cache from prefill to decode over a fast network.

Picture it: two pools
  1. A request reaches the router (which may first check for cached prefixes).
  2. A prefill GPU processes the prompt and produces the first token and the KV cache. Prefill nodes can use smaller parallel groups and favour compute.
  3. The cache moves to a decode GPU over RDMA or NVLink (libraries such as NVIDIA's NIXL). This is the new cost disaggregation adds.
  4. Decode GPUs run large, steady batches, so long prompts arriving elsewhere never stall them.
Try it: is the transfer worth it?

Llama-3-70B, KV in FP8 (160 KB per token); prefill on 8 H100s at 50% of peak.

Worth it at scale

  • DistServe, Splitwise and Mooncake showed big gains in requests that meet both TTFT and TPOT targets. NVIDIA Dynamo and llm-d package the pattern.
  • For a few GPUs and short prompts, chunked prefill on shared GPUs is simpler and often enough.
Chapter 7.6

Cache-aware routing

“

Prefix caching only helps if the request lands on the replica that holds its cache. A round-robin load balancer scatters a conversation's turns across replicas, so they miss. A KV-aware router sends each request where its prefix already lives, while still watching load.

Try it: replicas vs cache hits
━ round-robin━ KV-aware (90% of sessions stay put)

Multi-turn chat; each replica caches what it has seen. Round-robin hit chance ≈ 1 ÷ replicas.

Route on prefix and load together

  • Pure stickiness overloads popular replicas; pure load balancing throws caches away. Routers in Dynamo, llm-d and SGLang score both. At minimum, use session affinity for multi-turn traffic.

Running it in production

Benchmark honestly, plan capacity, watch the right signals and fail gracefully.

Chapter 8.1

Benchmarking that tells the truth

“

Peak tokens per second on a fixed batch tells you little. Benchmark with your real prompt and output lengths, requests arriving at random, and a sweep of load levels. Then report goodput: the request rate you can serve while still meeting your latency targets.

Try it: throughput vs goodput
━ throughput (all requests)━ goodput (requests within target)

Illustrative replica with a ceiling of 10 requests/s. As load rises, queues and bigger batches push p99 latency past the target well before throughput tops out.

import asyncio, random, time
from openai import AsyncOpenAI
client = AsyncOpenAI(base_url="http://localhost:8000/v1", api_key="x")

async def one(prompt, max_tokens):
    t0 = time.perf_counter(); stamps = []
    stream = await client.completions.create(model="m", prompt=prompt, max_tokens=max_tokens, stream=True)
    async for _ in stream:
        stamps.append(time.perf_counter())
    ttft = stamps[0] - t0
    itl = [b - a for a, b in zip(stamps, stamps[1:])]   # inter-token latencies
    return ttft, itl

async def run(rate_per_s, requests):                     # open loop: Poisson arrivals
    tasks = []
    for prompt, n in requests:
        tasks.append(asyncio.create_task(one(prompt, n)))
        await asyncio.sleep(random.expovariate(rate_per_s))
    return await asyncio.gather(*tasks)

Use the standard tools, with your data

  • vLLM's benchmark scripts, NVIDIA GenAI-Perf/AIPerf and GuideLLM all sweep load and report percentiles. Feed them samples of your real prompts and output lengths.
Chapter 8.2

Capacity planning

“

Little's law: requests in the system = arrival rate × time each spends there. Your peak arrival rate and the time a request takes give the concurrency you must hold. Memory and your latency target give how many requests one replica can hold. Divide, and add headroom.

Try it: size a fleet (8B model, one H100 per replica)

Per-replica limit = largest batch whose decode step stays under the TPOT target and whose KV cache fits (same model as Floor 1). 30% headroom for bursts and failures. Real plans start from a benchmark, not this formula.

Plan for the peak and the tail

  • Size for peak-hour traffic and for p99 lengths, not daily averages. Keep headroom so losing a replica doesn't breach targets, and know how long scaling up takes.
Chapter 8.3

Observability

“

Inference needs its own dashboard. Latency per phase, queue depth and KV cache use tell you what's wrong; GPU utilisation mostly doesn't.

Try it: read the dashboard

  • TTFT and inter-token latency (p50/p99), end-to-end latency, waiting and running requests, KV cache usage, preemptions, prefix-cache hit rate, prompt and output length histograms, tokens/s, errors. Engines expose these as Prometheus metrics.
  • Trace a request across router, prefill, transfer and decode when you disaggregate.
Chapter 8.4

“

When demand exceeds capacity, an unprotected server queues everything and everyone times out. Decide in advance who waits, who gets a fast "try later", and what degrades, so most users still get good service.

Economics and decisions

Turn GPU hours into cost per token, choose between buying and building, and pick the next optimisation.

Chapter 9.1

Cost per million tokens

“

Cost per token = what the GPUs cost per hour ÷ tokens they produce per hour. Batch size and utilisation move the bottom of that fraction more than anything else, which is why the same GPU can be cheap or ruinous.

Try it: price your own tokens

2,000-token contexts. Output = decode at this batch size; input = prefill at 50% of peak FLOPs. Utilisation = average load ÷ the load you provisioned for. Your measured throughput should replace these estimates.

Why APIs charge more for output

  • Input tokens are prefilled in parallel and are compute-efficient; output tokens are made one step at a time. Expect output to cost several times more per token, here and on any price list.
  • Idle GPUs still bill. Utilisation is a cost lever as large as any kernel.
Chapter 9.2

AvailabilityThe GPU you can actually get, in your region, often decides.

Benchmark the shortlist

  • Run your model, engine and traffic on two or three options for a day each. Paper specs predict the shape, not the winner.

    Chapter 9.5

    On device and at the edge

    “

    The same maths applies on a laptop or phone: one user, batch 1, completely memory-bound. Tokens per second ≈ memory bandwidth ÷ model bytes, and the model must fit in the memory the device can spare. That's why on-device models are small and 4-bit.

    Try it: what runs where

    Ceiling from bandwidth alone; real speeds are lower. "Usable" memory leaves room for the OS and apps. Phone and laptop figures are typical examples.

    Why on-devicePrivacy, offline use, no per-token cost, low latency for short tasks.
    LimitsSmall models, battery and heat, slow prefill on long prompts.
    Toolsllama.cpp/GGUF, Ollama, MLX on Apple silicon, ONNX Runtime, ExecuTorch; platform models such as Apple's on-device foundation model and Gemini Nano.

    Hybrid is common

    • Run a small model on device for quick, private tasks and fall back to the cloud for hard ones. The routing decision is the same cascade idea as Floor 6.
