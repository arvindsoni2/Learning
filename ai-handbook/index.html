How models learn

The ideas under every AI system: what learning means, why data and measurement matter, and how numbers come to stand for meaning.

Chapter 1.1

AI, ML and deep learning

“

AI is the goal: machines doing tasks that seem to need intelligence. Machine learning is one way to get there, by learning rules from examples. Deep learning, and the LLMs inside it, is one kind of machine learning.

Picture it
AI, not MLA rules engine that routes tickets by keyword. A chess program searching moves.
ML, not deepA spam filter or a delivery-time predictor trained on a table of past orders.
Deep learningRecognising faces, transcribing speech, spotting bruised fruit in a photo.
GenAI & LLMsModels that produce new text, images or code: chat assistants, coding agents.
Picture it: rules vs learning
All AI is machine learning.
→
Hand-written rules count as AI too. Most production "AI features" are a few rules wrapped around one model.

Rule first, model second

  • Before reaching for a model, check whether a rule, a lookup or a SQL query solves it. Those are cheaper, testable and explainable.
  • Use a model where the rules are too many or too fuzzy to write down: free-text emails, photos, voice.
Chapter 1.2

Three ways to learn

“

Supervised learning copies labelled answers. Unsupervised learning finds structure with no labels. Reinforcement learning tries things and keeps what earns a reward. LLMs are trained with all three.

SupervisedA teacher gives the answer for every example. The model learns to reproduce it on new inputs.
UnsupervisedNo answers at all. The model groups similar things or spots the odd one out.
ReinforcementTry, get a score, adjust. Used to train game-players, robots, and to tune chat models from feedback.
Try it: sort the problems

How LLMs use all three

  1. Pretraining is self-supervised: hide the next word in real text and predict it. The labels come free from the text itself, so it scales to trillions of words.
  2. Fine-tuning is supervised: people write example prompts and ideal answers.
  3. Preference tuning uses reinforcement: answers people (or a reward model) prefer get reinforced.

Labels cost money

  • For a supervised feature, budget for labelling: who tags the examples, how many, and how you check their consistency.
  • A pretrained LLM often needs only a handful of examples in the prompt, which is why it can beat a custom model on small, messy problems.

Chapter 1.4

Overfitting

“

A model that memorises its training data looks brilliant in testing and stumbles on anything new. You want the simplest model that still captures the pattern.

Try it: make the model more flexible

Teal dots are training data, coral dots are new data. The line is the model. Raise its flexibility (polynomial degree) and watch training error fall while new-data error climbs.

0new-data error

Cures for overfitting

  • More, more varied data, so memorising stops paying off.
  • A simpler model or fewer features.
  • Regularisation: a penalty for extreme weights.
  • Early stopping: stop training when validation error starts to rise.
import numpy as np
rng = np.random.default_rng(0)
x = np.linspace(-1, 1, 14);  y = np.sin(2.5 * x) + rng.normal(0, .25, 14)
x_new = np.linspace(-.95, .95, 10);  y_new = np.sin(2.5 * x_new) + rng.normal(0, .25, 10)

for degree in (1, 3, 12):
    coefs = np.polyfit(x, y, degree)           # fit on training data only
    err = lambda xs, ys: np.sqrt(np.mean((np.polyval(coefs, xs) - ys) ** 2))
    print(degree, "train", round(err(x, y), 2), "new", round(err(x_new, y_new), 2))

Prompts overfit too

  • A prompt tuned until five demo examples look perfect is overfitted. Test it on fifty real ones before anyone signs off.
  • "Great demo, poor launch" is usually overfitting to the demo data.

Chapter 1.6

Neural nets and gradient descent

“

A neural net is layers of simple weighted sums, each followed by a bend. Training nudges the weights downhill on an error landscape, one small step at a time.

Picture it: one tiny network
One neuronz = w₁x₁ + w₂x₂ + w₃x₃ + bout = max(0, z)Weigh each input, add them up, then bend: negatives become zero. Stack thousands of these in layers and the bends let the network draw curved, complicated boundaries.
Try it: roll down the error hill

The curve is the model's error for each value of one weight. Each step moves the weight against the slope. The learning rate is the step size.

0.10
Too small a stepSafe but slow, and it settles in the first dip it finds, even if a deeper valley sits next door.
Too big a stepIt overshoots, bounces between walls, or flies off entirely. Try 1.0 above.

Backpropagation in one line

To find the slope for millions of weights at once, the error is passed backwards through the layers with the chain rule from calculus. Each weight learns how much it contributed to the mistake.

You'll rarely train from scratch

  • Product teams mostly use pretrained models. Training from zero needs huge data and compute.
  • The same knobs appear when you fine-tune: learning rate, epochs, early stopping. Now you know what they do.
Chapter 1.7

Embeddings

“

An embedding turns a word, sentence or image into a list of numbers, placed so that similar meanings sit close together. Search, RAG and recommendations all run on this.

Try it: a meaning map

Real embeddings have hundreds or thousands of dimensions; this map squashes a few phrases into two. Tap a phrase to see its nearest neighbours.

import numpy as np

def cosine(a, b):
    """1.0 = same direction (same meaning), 0 = unrelated."""
    return float(a @ b / (np.linalg.norm(a) * np.linalg.norm(b)))

# in real life these vectors come from an embedding model API
refund   = np.array([0.81, 0.12, 0.55])
money_back = np.array([0.78, 0.18, 0.60])
delivery = np.array([0.10, 0.92, 0.31])
print(cosine(refund, money_back), cosine(refund, delivery))   # ~0.99 vs ~0.37
Close vectors mean the same thing.
→
Close vectors appear in similar contexts. "Hot" and "cold" often sit close because they're used the same way, even though they're opposites.

The embedding model is a design choice

  • Search quality depends heavily on which embedding model you pick, especially for non-English text or specialist jargon. Test two or three on your own data.
  • Changing the embedding model means re-embedding every stored document. Plan for it.

LLMs up close

What a large language model is actually doing, how it was trained, and where its limits come from.

Chapter 2.1

How an LLM writes a sentence

“

An LLM is a next-token guesser, run in a loop. It never writes a whole answer at once. It writes one token, adds it to the text, and guesses again.

Picture it: the loop
Text inYou send a prompt. So far it's only characters.
TokensText is chopped into word-pieces, each with an ID number.
VectorsEach token becomes a list of numbers: its embedding.
AttentionEach token looks back at the others and weighs which ones matter.
ProbabilitiesEvery token in the vocabulary gets a score for "what comes next".
Pick & repeatOne token is drawn, added to the end, and the loop runs again.

…until it draws a "stop" token or hits the length limit ↺

Try it: see your words as tokens

Models see tokens, not letters or words. A common English word is usually one token; a rare one is split into pieces.

0characters
0words
0tokens (approx.)

Rule of thumb for English: 1 token ≈ 4 characters ≈ ¾ of a word. "·" marks a leading space.

This toy splitter imitates the idea; real tokenisers learn their vocabulary from data, so counts differ by model. Hindi and other non-Latin scripts usually need more tokens per word.

Try it: attention

"Bank" could mean money or a riverside. Attention lets the model settle it by looking at the other words. Tap a word to see where it looks.

Weights are illustrative. Real models run dozens of these "heads" in parallel, each looking for a different pattern, across dozens of layers.

Try it: temperature
The chef ordered fresh ___

The model gives each candidate a raw score (a logit). Temperature reshapes those scores before one is drawn: low plays safe, high takes chances.

1.0

import numpy as np
words  = ["basil", "fish", "bread", "herbs", "tomatoes", "gravel"]
logits = np.array([3.2, 2.9, 2.5, 2.2, 1.8, -1.0])   # raw scores from the model

def next_token_probs(logits, temperature=1.0):
    if temperature == 0:                     # greedy: always the top token
        p = np.zeros_like(logits); p[logits.argmax()] = 1.0
        return p
    z = logits / temperature                   # low T sharpens, high T flattens
    z = z - z.max()                            # keeps exp() from overflowing
    return np.exp(z) / np.exp(z).sum()         # softmax: scores -> probabilities

for t in (0.2, 1.0, 1.8):
    p = next_token_probs(logits, t)
    print(t, np.random.choice(words, p=p), p.round(2))
It reads words.
→
It reads tokens. That's why it can stumble on spelling and counting letters.
Temperature 0 means correct.
→
Temperature 0 means most likely. The most likely answer can still be wrong.

Tokens are the unit of everything

  • Extraction (fields out of emails or invoices): low temperature for repeatable answers. Drafting: 0.7–1.0 for variety. Some newer models fix sampling for you; check the docs.
  • You pay per token in and out, the context limit counts tokens, and latency grows with output length because tokens come one at a time.
Chapter 2.2

How an LLM is trained

“

Pretraining on huge amounts of text builds a knowledgeable autocomplete. Later stages teach it to follow instructions, prefer helpful and safe answers, and reason through problems that can be checked.

Picture it: step through the stages
  1. Pretraining. Predict the next token across a vast slice of the internet, books and code. This is where nearly all knowledge and language skill comes from, and most of the compute bill. The result is a base model: brilliant autocomplete, no manners.
  2. Instruction tuning (SFT). Thousands of example conversations written or checked by people teach it to answer the question instead of just continuing the text.
  3. Preference tuning. The model writes two answers; people, or an AI judge following written principles, pick the better one. Reinforcement learning shifts the model towards the preferred style: helpful, honest, refusing harmful requests.
  4. Reasoning RL. On problems with checkable answers (maths, code with tests), the model is rewarded for getting it right, and learns to work through steps first. This is what produced today's reasoning models.
Base modelQ: What's the capital of France? Q: What's the capital of Spain? Q: What's the capital of…It just continues the pattern.
After tuningQ: What's the capital of France? A: Paris.It answers, because it learned the assistant role.
It learns from our chats as we talk.
→
The weights are frozen after training. Your conversation only changes what's in the context window, not the model.

Know the cut-off

  • Every model has a training cut-off date. Anything newer (prices, policies, your own data) must be supplied in the prompt or through retrieval.
  • Check the provider's data-use terms: whether API traffic may be used for future training, and how long it's kept.
Chapter 2.3

The context window

“

The context window is everything the model can see in one call: instructions, history, documents, tool definitions and its own answer. It's measured in tokens, and filling it costs money, time and focus.

Try it: pack a context window
200k
Picture it: lost in the middle

Illustrative. Research found models recall facts at the start and end of a long context better than those buried in the middle. Newer models have narrowed the gap, but putting the key material first or last still helps.

A million-token window means I can skip search.
→
You can, but each call gets slower and dearer, and accuracy drops as the haystack grows. Send the relevant pages, not the library.

Context is a budget

  • Set a token budget per call the same way you set a performance budget for a web page.
  • Tool definitions quietly eat space: thirty tools with long descriptions can cost more than the question.

Reasoning models write a chain of thought before they answer. Extra thinking tokens buy accuracy on hard, multi-step problems, and cost time and money on easy ones.

Not worth itExtracting fields, classifying tickets, rewording text, quick lookups. Use a fast model with low or no thinking.

→
Reasoning text is useful for debugging but isn't a guaranteed faithful record of what drove the answer. Judge the outcome.

Make effort a setting

  • Thinking tokens are billed like output tokens, and they add seconds before the first visible word.
Chapter 2.5

Hallucination

“

A model is trained to produce plausible text. When it doesn't know, it can produce plausible fiction with full confidence. You can shrink the risk and catch it, but not switch it off.

Picture it: how a confident wrong answer happens
A rare question"Which clause of supplier contract 4471 covers late fees?"
No memory of itThe model never saw that contract. There's no strong pattern to follow.
Fluency wins"Clause 7.2" is a very likely-looking continuation for contract questions.
Confident toneNothing in next-token prediction says "and sound unsure". Out comes a crisp, wrong answer.
The mitigation ladder (climb as stakes rise)

Design the "not sure" path

  • Every AI feature needs a route for low-confidence cases: ask the user, flag for a person, or fall back to a rule.
  • Track a hallucination rate in your evals (Floor 7) and set a go-live bar for it.
Chapter 2.6

Choosing a model

“

There's no best model, only the best fit for a task's quality bar, speed and budget. Prove the task is possible with a strong model, then try smaller ones against your evals.

Try it: a first recommendation
OptionGood forWatch out for
Frontier API modelHard reasoning, agents, coding, best qualityHighest price per token; data leaves your network
Small, fast API modelHigh-volume extraction, classification, routingFails on multi-step or ambiguous tasks

Prove big, ship small

  • Hide the model behind your own interface so swapping is a config change, then re-run evals every time a new model ships.
  • Ask about region, retention and support before price: they decide what's allowed in a regulated business.
Chapter 2.7

Beyond text

“

Images, PDFs and audio are turned into tokens too, so the same model can read a delivery note or listen to a call. They fail differently from text: small print, tables, counting and layout trip them up.

Picture it: an image becomes tokens
Usually strongDescribing photos, reading clean printed documents, pulling fields from forms, transcribing clear speech, reading screenshots and charts at a glance.
Usually weakTiny or handwritten text, dense tables, exact counting, precise positions, low-quality scans, overlapping speakers.

Test with ugly inputs

  • For document extraction, build your test set from the worst real scans and phone photos, not the clean samples from the supplier.
  • Images cost tokens too, often hundreds to thousands per page. Resize before sending where detail allows.

Chapter 3.2

  
Structured output

  
“
When code reads the answer, ask for JSON that matches a schema, validate it, and have a plan for when it doesn't fit: retry with the error, then hand off to a person.

  

    
Free textSure! It looks like the customer wants about a dozen boxes of tomatoes, maybe delivered Tuesday?Friendly, unparseable, vague.

    
Schema{"items": [{"sku": "TOM-500G",
  "qty": 12}],
 "delivery_date": "2026-11-24",
 "confidence": "medium"}Your system can act on this.

  

  
Picture it: the validate-and-retry loop

  

    

    
    
      
  1. The model gets the email plus a schema: what fields, what types, what's allowed.
    2. 
      
  2. It returns JSON. Your validator checks the shape and business rules: quantity above zero, SKU exists, date not in the past.
    3. 
      
  3. If validation fails, send the error back ("qty must be a positive integer") and ask again. One or two retries fix most slips.
    4. 
      
  4. Valid output flows straight into the downstream system. This is the "no-touch" path.
    5. 
      
  5. Still failing after retries, or confidence is low? Route to a person. That's not failure; it's the design.
    6. 
    

  

  
from pydantic import BaseModel, Field, ValidationError

class Line(BaseModel):
    sku: str
    qty: int = Field(gt=0)

class Order(BaseModel):
    items: list[Line]
    delivery_date: str
    confidence: str  # "high" | "medium" | "low"

def extract(email, call_model, max_tries=3):
    feedback = ""
    for _ in range(max_tries):
        raw = call_model(email, schema=Order.model_json_schema(), feedback=feedback)
        try:
            order = Order.model_validate_json(raw)
            if order.confidence != "low":
                return order                    # no-touch path
        except ValidationError as e:
            feedback = str(e)                   # tell the model what was wrong
    return None                                 # -> human queue


  
Structured-output mode means the data is right.
→
It guarantees the shape, not the truth. A perfectly formatted order can still have the wrong quantity. Validate the business rules too.

  
The schema is a contract
  • Treat the schema like an API contract with the downstream team: version it, review changes, and test old examples against new versions.
  • Agree the no-touch rate target and the human-queue process before go-live.

“

Picture it: one tool call, step by step

    2.

    3.

  • Start read-only. Add tools that change data only with limits and an approval step (Floor 5).

“
A prompt is one message. Context engineering decides what the model sees on every turn: which instructions, history, documents and tools go in, and what gets dropped, summarised or saved outside.

import random, time

def call_with_backoff(fn, tries=5, base=1.0, cap=30.0):
    for attempt in range(tries):
        try:
            return fn()
        except TransientError:                        # 429, 5xx, overloaded
            if attempt == tries - 1:
                raise
            wait = min(cap, base * 2 ** attempt)      # 1, 2, 4, 8 ... seconds
            time.sleep(random.uniform(0, wait))       # "full jitter" spreads clients out

  • Ask what happens at peak: how many calls per minute, what your rate limit is, and what users see when you hit it.
  • Set spend alerts and per-user limits on day one. Runaway loops are a real way to burn a monthly budget overnight.

Chapter 4.1

Chapter 4.2

  
The RAG pipeline

  
“
Retrieval-augmented generation has two halves. Ahead of time you chop, embed and store your documents. At question time you find the most relevant pieces and hand them to the model with the question.

  
Picture it: step through both halves

  

    

    
    
      
  1. Load and clean. PDFs, web pages, tickets. Strip boilerplate, keep headings and tables readable. This step decides quality more than any model choice.
    2. 
      
  2. Chunk and embed. Split into passages (4.3) and turn each into a vector with an embedding model (1.7).
    3. 
      
  3. Store. Vectors plus the original text and metadata go into a vector store. Keep it in sync: updates and deletions too.
    4. 
      
  4. Search. The question is embedded the same way and the store returns the nearest chunks, usually with keyword search alongside (4.4).
    5. 
      
  5. Rerank and trim. A reranker re-reads the top 20–50 and keeps the best handful that fit your context budget.
    6. 
      
  6. Generate. The model answers using only those passages and cites which ones it used.
    7. 
    

  

  
import numpy as np

def build_index(docs, embed):
    chunks = [c for d in docs for c in chunk(d.text, size=300, overlap=50)]
    vectors = np.array([embed(c) for c in chunks])
    vectors /= np.linalg.norm(vectors, axis=1, keepdims=True)
    return chunks, vectors

def answer(question, chunks, vectors, embed, llm, k=4):
    q = embed(question); q /= np.linalg.norm(q)
    top = np.argsort(vectors @ q)[::-1][:k]              # nearest chunks
    context = "\n\n".join(f"[{i}] {chunks[i]}" for i in top)
    prompt = (f"Answer using only the sources below. Cite [numbers]. "
              f"If they don't contain the answer, say so.\n\n{context}\n\nQ: {question}")
    return llm(prompt)


  
RAG stops hallucination.
→
It reduces it. The model can still pick the wrong passage, misread a table or ignore the sources. Measure it (4.6).

  
The pipeline is the product
  • Most RAG effort goes into ingestion: messy PDFs, tables, duplicates, and keeping the index current when documents change or are deleted.
  • Name an owner for each source. Stale documents produce confidently stale answers.

Chapter 4.4

  
Finding the right passages

  
“

  • Add a reranker before you add complexity elsewhere; it's often the cheapest quality jump.

Chapter 5.1

def run_agent(goal, tools, model, max_steps=15, max_cost=0.50):
    messages, cost = [{"role": "user", "content": goal}], 0.0
    for step in range(max_steps):
        reply = model.call(messages, tools=tools)
        cost += reply.cost
        messages.append(reply.as_message())
        if reply.stop_reason != "tool_use":
            return reply.text                       # the agent decided it's done
        if cost > max_cost:
            return "Stopped: cost limit reached"     # never loop forever on your card
        for call in reply.tool_calls:
            messages.append(tool_result(call.id, tools.run(call)))
    return "Stopped: step limit reached"

  • Set a step limit, a time limit and a cost limit for every agent, and decide what the user sees when one is hit.
  • Save the full trace of every run. You can't improve what you can't replay.

JUDGE = """You are checking a customer reply for FAITHFULNESS only.
Sources: {sources}
Reply: {reply}
Does every factual claim in the reply appear in the sources?
Answer with JSON: {{"reason": "...", "verdict": "pass" | "fail"}}"""

def agreement(judge_labels, expert_labels):
    pairs = list(zip(judge_labels, expert_labels))
    caught = sum(j == e == "fail" for j, e in pairs) / max(1, expert_labels.count("fail"))
    spared = sum(j == e == "pass" for j, e in pairs) / max(1, expert_labels.count("pass"))
    return caught, spared        # aim high on both before trusting the judge


  
Trust, then verify the judge
  • Hold back some expert-labelled cases to test the judge; never tune its prompt on all of them.
  • Re-check agreement when you change the judge model or prompt. A silent judge drift corrupts every dashboard downstream.

Chapter 8.1

  
Where attacks come in

  
“

Chapter 8.2

  
Prompt injection

  
“
Models can't reliably tell instructions from data. Text hidden in an email, web page or document can redirect an agent. There's no complete fix like parameterised queries for SQL, so you design for containment.

  
Picture it: an indirect injection, step by step

  

    

    
    
      
  1. A user asks their assistant to summarise the inbox. Innocent.
    2. 
      
  2. One email, from anyone at all, contains hidden instructions. The user never sees them.
    3. 
      
  3. The agent reads every email as part of the task. To the model, the hidden text looks just like an instruction.
    4. 
      
  4. If the agent can send email, it may obey: private invoices leave the company. Nobody "hacked" anything; the agent did its job for the wrong boss.
    5. 
      
  5. Containment: the summarising agent has no send tool, or sending needs a person's approval. The injection still happens; it just can't do damage.
    6. 
    

  

  

    
Direct injectionThe user types the attack: "ignore your rules and…". Also called jailbreaking. Mostly a risk to your policies and brand.

    
Indirect injectionThe attack hides in content the agent reads. Far more dangerous: the attacker never talks to your system directly.

  

  
A strong system prompt stops injection.
→
Prompt wording reduces it, but it isn't a control. Limits on what the agent can access and do are the control.

  
Assume it will be fooled
  • Ask of every agent: "If this agent obeyed an attacker for one step, what's the worst it could do?" Then shrink that.
  • Test with injection attempts in your eval suite, especially in documents and tool results.

“

Sneaky exits"Send data out" includes more than email: a web request, a link the user clicks, even an image URL with data in its address.

    
Split the rolesOne agent reads untrusted content with no private access; another holds private data and never reads raw outside text.

Chapter 8.4

  
Containment

  
“
Assume the model will sometimes be fooled or simply wrong. Limit what a fooled model can do with layers that don't depend on the model behaving: permissions, sandboxes, rules in code, approvals, limits and logs.

  
Picture it: defence in depth

  

  

    
FragileThe agent uses one admin database login for everyone, and the prompt says "only show the user their own orders".

    
ContainedEach call runs with the signed-in user's own permissions, so even a fooled agent can only see what that user could see.

  

  
Authorisation lives in code
  • Never let the model decide who's allowed to do what. It can request; your code checks.
  • Give every agent its own identity and credentials, scoped to the task, so its actions are traceable and revocable.

Chapter 9.2

  
Making serving fast

  
“
Serving engines squeeze more answers out of the same GPUs: batching many requests together, caching work already done, storing weights in fewer bits, and guessing several tokens ahead.

  

    
Continuous batchingThe GPU works on many requests at once and slots new ones in as soon as others finish, instead of waiting for the whole batch.

    
KV cacheAttention data for earlier tokens is kept so each new token doesn't recompute the whole sequence. It eats GPU memory, so engines page it like an operating system.

    
Prefix cachingWhen many requests share the same opening (system prompt, tools, documents), that work is done once and reused. This is what makes prompt caching cheap.

    
QuantisationStore weights in 8 or 4 bits instead of 16. The model needs half or a quarter of the memory and runs faster, usually with a small quality loss you should measure.

    
Speculative decodingA small, fast model drafts several tokens; the big model checks them all in one pass and keeps the ones it agrees with. Same output, fewer slow steps.

    
Routing & load balancingSend requests with the same prefix to the same server to reuse its cache; spread the rest by load.

  

  
Try it: will it fit on the GPU?

  

    

    

      
    

    

    

  

  
You rent this or you run it
  • With an API, the provider does all of this; you see it as price and speed. Self-hosting means your team owns these choices and their trade-offs.
  • Quantised open models can run on surprisingly small hardware, but evaluate quality on your task before committing.







  
Chapter 9.3

  
Cost and routing

  
“
Cost is calls × tokens × price. The big levers are sending fewer tokens, routing easy cases to a cheaper model, and caching what repeats. Measure cost per successful task, not per call.

  
Try it: a monthly bill

  

    

    

    

    

    

    

    
Example prices only: large model $3 in / $15 out per million tokens; small model $0.80 / $4; cached input at a tenth of the normal input price. Check your provider's current prices.

  

  
def monthly_cost(calls_per_day, tin, tout, routed=0.0, cached=0.0,
                 big=(3.0, 15.0), small=(0.8, 4.0), cache_discount=0.1):
    def per_call(price_in, price_out):
        effective_in = tin * (1 - cached) + tin * cached * cache_discount
        return (effective_in * price_in + tout * price_out) / 1e6
    blended = (1 - routed) * per_call(*big) + routed * per_call(*small)
    return blended * calls_per_day * 30

print(round(monthly_cost(20_000, 4_000, 400)))                          # baseline
print(round(monthly_cost(20_000, 4_000, 400, routed=0.7, cached=0.6)))  # after levers


  
Unit economics first
  • Express cost per outcome: per order processed, per ticket resolved. Compare it with the cost of the manual process it replaces.
  • A router that sends easy cases to a small model only pays off if your evals prove the small model handles them.
