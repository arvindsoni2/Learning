Chapter 1.1

Global infrastructure

2.2 highly available3.4 network
“

A Region is a separate geographic area. Inside it, Availability Zones are isolated groups of data centres a few miles apart. Spread across AZs to survive a data-centre failure; across Regions to survive a regional one.

Picture it
Try it: which extension of AWS?
An Availability Zone is one data centre.
→
An AZ is one or more data centres with independent power and networking. Most Regions have three or more AZs.

Choosing where

"data must stay in the country"→Pick the Region; data doesn't leave it unless you move it "survive the loss of a data centre"→Multi-AZ "survive a Region outage"→Multi-Region (Floor 9) "lowest latency for global users"→Edge: CloudFront or Global Accelerator
Chapter 1.2

Shared responsibility

1.2 workloads1.3 data
“

AWS secures the cloud: buildings, hardware, the virtualisation layer. You secure what you put in it: your data, who can access it, and whatever you configure. The more managed the service, the more AWS takes on.

Try it: slide from EC2 to serverless

you   AWS

AWS patches the operating system on my EC2 instances.
→
On EC2 the guest OS is yours to patch (Systems Manager Patch Manager helps). On RDS and Lambda, AWS patches it.

Spot the shift

"least operational overhead"→The more managed option: RDS over a database on EC2, Fargate over EC2 for containers "who is responsible for encrypting the data?"→Always you: you choose to turn it on and who holds the keys

Chapter 1.4

How to read an exam question

all domains
“

In most questions, several options would technically work. The qualifier (most cost-effective, least operational overhead, highest availability, most secure) is what picks the winner. Find it first.

Picture it: anatomy of a question
Context · A company runs a web app on EC2 instances behind an ALB in one AZ.
Requirement · The app must stay available if an AZ fails.
Qualifier · with the LEAST operational overhead.
Options · Four plausible answers. Usually two are clearly wrong and two "work".

Here: an Auto Scaling group across two or more AZs behind the ALB. A custom script that launches instances elsewhere also "works", but carries far more operational overhead.

Try it: match the qualifier to the usual winner
Eliminate firstStrike options that break a stated requirement, then compare the survivors on the qualifier.
Prefer the built-in featureA managed feature beats custom code on EC2 or Lambda almost every time.
Read "choose TWO"Multiple-response questions say how many to pick. Each pick must be right on its own.

Mind the keywords

"without managing servers"→Lambda, Fargate, Aurora Serverless, DynamoDB "minimise changes to the application"→Lift-and-shift friendly: RDS for the same engine, EFS for shared files "near real-time"→Streaming (Kinesis), not nightly batch

Identity & governance

Who can do what to which resource: IAM, temporary credentials, multi-account control and sign-in for staff and customers.

Chapter 2.1

Users, groups and roles

1.1 secure access
“

Policies grant permissions. Groups collect users so you attach policies once. Roles hand out temporary credentials to whoever is allowed to assume them: an EC2 instance, a Lambda function, another account, or a federated user.

Picture it
Root userTurn on MFA, delete its access keys, lock it away. Use it only for the few tasks that need it, such as closing the account.
Least privilegeGrant only what's needed. Start from AWS managed policies, then tighten with customer managed ones. IAM Access Analyzer helps find unused access.
PeoplePrefer IAM Identity Center for humans (2.5). Enforce MFA. Avoid long-lived access keys.
Store an access key on the EC2 instance so the app can reach S3.
→
Attach an IAM role (via an instance profile). The app gets rotating temporary credentials automatically; nothing to leak.

Who's asking?

"application on EC2 needs to access…"→IAM role with an instance profile "Lambda function needs to write to DynamoDB"→Lambda execution role "secure the root account"→MFA, no access keys, don't use day to day
Chapter 2.2

How policies are evaluated

1.1 secure access
“

Everything starts denied. An explicit deny anywhere always wins. Otherwise, the request must be allowed by every guardrail that applies (SCPs, permissions boundaries) and by at least one granting policy (identity or resource).

Try it: the evaluator

A user in a member account calls s3:GetObject on a bucket in the same account. Switch each policy's verdict.

# An identity policy, shown as a Python dict (IAM policies are JSON)
policy = {
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject"],
    "Resource": "arn:aws:s3:::reports-bucket/finance/*",
    "Condition": {"Bool": {"aws:MultiFactorAuthPresent": "true"}}
  }]
}
# Effect + Action + Resource (+ optional Condition). Anything not allowed is denied.
An Allow in one policy overrides a Deny in another.
→
Explicit Deny always wins, wherever it is. That's why guardrails are written as denies.

Guardrails vs grants

"developers may create roles but must not exceed their own permissions"→Permissions boundary "no account in the organisation may use regions outside the EU"→SCP with a Deny on aws:RequestedRegion "only when using MFA / from the corporate IP range"→Policy Condition keys
Chapter 2.3

Temporary credentials and cross-account access

1.1 secure access
“

AWS STS issues short-lived credentials when a principal assumes a role. Cross-account access is a role in the target account whose trust policy names the other account; nobody shares passwords or keys.

Picture it: step through a cross-account assume
  1. A pipeline in the tools account needs to deploy to production, which is a separate account.
  2. Production has a role whose trust policy allows Account A to assume it, and whose permissions policy allows only deployment actions.
  3. The pipeline calls STS AssumeRole. Account A must also allow it to do so.
  4. STS returns temporary credentials that expire on their own (one hour by default).
  5. The pipeline acts in production with exactly the role's permissions, and CloudTrail records it.
External IDFor a third party assuming your role, require an external ID in the trust policy to prevent the "confused deputy" problem.
Instance profileThe container that hands an EC2 instance its role. The SDK fetches and refreshes credentials automatically.
FederationCorporate users sign in through SAML or OIDC and receive role credentials, with no IAM users at all.

Signals

"grant a third-party auditor access to our account"→Cross-account role with external ID "avoid long-term credentials"→Roles and STS
Chapter 2.4

Organizations, SCPs and Control Tower

1.1 secure access4.x billing
“

AWS Organizations groups accounts into organisational units with one consolidated bill. Service control policies set the maximum permissions for accounts in an OU; they never grant anything. Control Tower builds and governs a multi-account landing zone for you.

Picture it: an organisation
Consolidated billingOne bill; usage is pooled for volume discounts, and Reserved Instance and Savings Plans discounts can be shared across accounts.
SCPA filter on what IAM in member accounts can grant. Use denies for guardrails: no leaving the organisation, no disabling CloudTrail.
Control TowerSets up a landing zone: account factory, log archive and audit accounts, and preventive and detective controls, with a dashboard.
An SCP that allows S3 gives users S3 access.
→
SCPs only limit. Users still need an IAM policy that grants S3 inside the account.

Signals

"centrally prevent all accounts from…"→SCP on the OU or root "set up and govern a secure multi-account environment quickly"→AWS Control Tower "single bill, share Reserved Instance discounts"→Organizations consolidated billing
Chapter 2.5

Workforce and customer identity

1.1 secure access1.2 workloads
“

Staff sign in once to many AWS accounts through IAM Identity Center, often backed by your existing directory. Your app's customers sign up and sign in through Amazon Cognito.

Try it: match the need to the service
Cognito user poolsA user directory for your app: sign-up, sign-in, MFA, social and SAML login. Returns tokens (JWTs) your app or API Gateway checks.
Cognito identity poolsSwap a login (from a user pool, Google, etc., or a guest) for temporary AWS credentials, e.g. to upload straight to S3 from a mobile app.

Signals

"employees use existing Active Directory credentials across many AWS accounts"→IAM Identity Center + AD (AWS Managed Microsoft AD or AD Connector) "mobile app users sign in with Google and upload photos to S3"→Cognito user pool + identity pool "run Windows workloads that need a real AD domain in AWS"→AWS Managed Microsoft AD
Chapter 2.6

Resource policies and sharing

1.1 secure access1.3 data
“

Some resources carry their own policy saying who may use them: S3 buckets, KMS keys, SQS queues, SNS topics, Lambda functions. Resource Access Manager shares whole resources, such as subnets or Transit Gateways, with other accounts.

Identity-basedAttached to a user, group or role: "this principal may do X to Y". No Principal element.
Resource-basedAttached to the resource: "principal P may do X to me". Has a Principal element, so it can name other accounts directly.
S3 bucket policyCross-account access, force HTTPS (aws:SecureTransport), restrict to a VPC endpoint, allow CloudFront via origin access control.
KMS key policyEvery KMS key has one; without it nobody, not even admins, can use the key.
Resource Access ManagerShare VPC subnets, Transit Gateways, Route 53 Resolver rules and more across accounts in the organisation, without copying them.
Making a bucket public is the easiest way to share it with a partner account.
→
A bucket policy naming the partner's account (or a role they assume) shares it privately. Keep Block Public Access on.

Signals

"only allow access to the bucket from our VPC"→Bucket policy condition on aws:SourceVpce "several accounts share one network"→VPC sharing with RAM "deny any request not using HTTPS"→Bucket policy deny when aws:SecureTransport is false

Chapter 3.2

Routes, gateways and NAT

1.2 workloads2.2 highly available4.4 network cost
“

Route tables decide where traffic leaves a subnet. An internet gateway gives public subnets two-way internet access. A NAT gateway lets private subnets reach out (for updates, APIs) without anyone reaching in.

Picture it: step through outbound traffic
  1. A private instance needs to download a patch. Its subnet's route table sends 0.0.0.0/0 to the NAT gateway.
  2. The NAT gateway sits in a public subnet and swaps the private source address for its own Elastic IP.
  3. The public subnet's route table sends internet traffic to the internet gateway.
  4. Replies come back the same way. Nothing on the internet can start a connection to the private instance.
NAT gateway is per AZFor high availability, put one NAT gateway in each AZ and point each private subnet at its own AZ's gateway.
It costs moneyHourly plus per-GB processed. Traffic to S3 or DynamoDB through NAT is wasted money; use gateway endpoints (3.4).
IPv6Use an egress-only internet gateway for outbound-only IPv6.
Run a NAT instance on EC2 to save effort.
→
NAT gateways are managed, scale automatically and need no patching. NAT instances are legacy.

Signals

"private instances need internet access for updates"→NAT gateway in a public subnet "NAT must survive an AZ failure"→One NAT gateway per AZ
Chapter 3.3

Security groups vs network ACLs

1.2 workloads
“

Security groups guard each instance, allow-only, and remember connections so replies flow back automatically. Network ACLs guard each subnet, can deny, and remember nothing, so return traffic needs its own rule.

Try it: will the HTTPS request get through?

A browser on the internet calls a web server in a public subnet on port 443. Toggle the rules.

Security groupNetwork ACL
Applies toNetwork interface (instance)Subnet
RulesAllow onlyAllow and deny, numbered, lowest number first
StateStateful: replies automaticStateless: allow return ports too
Neat trickReference another SG: "allow from the web tier's SG"Block a specific IP range quickly

Signals

"block a specific malicious IP address"→NACL deny rule (SGs can't deny), or WAF for HTTP "database should only accept traffic from the app tier"→DB SG allows the app tier's SG as source
Chapter 3.4

Private access to AWS services

1.2 workloads1.3 data4.4 network cost
“

VPC endpoints let private subnets reach AWS services without the internet or a NAT gateway. Gateway endpoints (S3 and DynamoDB only) are free route-table entries. Interface endpoints, powered by PrivateLink, put a private IP for the service in your subnet.

Gateway endpointS3 and DynamoDB only · added to route tables · no hourly charge · same Region only · not reachable from on-premises.
Interface endpoint (PrivateLink)Most services (SQS, KMS, Secrets Manager, S3 too…) · an ENI with a private IP · hourly and per-GB charge · reachable over VPN or Direct Connect.
Picture it: three ways to reach S3 from a private subnet
PrivateLink is only for AWS services.
→
You can publish your own service behind a Network Load Balancer as an endpoint service, and consumers in other VPCs connect privately without peering.

Signals

"private subnet must reach S3 without internet, lowest cost"→S3 gateway endpoint "on-premises servers reach S3 privately over Direct Connect"→S3 interface endpoint "expose a service to 100 customer VPCs, overlapping CIDRs"→PrivateLink endpoint service behind an NLB
Chapter 3.5

Connecting networks

3.4 network2.2 highly available4.4 network cost
“

Peering joins two VPCs, one-to-one and not transitive. Transit Gateway is a hub that connects many VPCs and on-premises networks. To reach your data centre: Site-to-Site VPN is quick and encrypted over the internet; Direct Connect is a private, consistent line that takes weeks to set up.

Try it: pick the link
Peering limitsNo overlapping CIDRs, no transitive routing (A–B and B–C doesn't give A–C), works across accounts and Regions.
Direct Connect + resilienceFor critical links: two connections at two locations, or a VPN as backup. Traffic isn't encrypted by default; add MACsec or run a VPN over it.

Signals

"dozens of VPCs and on-premises, simplify routing"→Transit Gateway "connect on-premises this week, encrypted"→Site-to-Site VPN "consistent bandwidth, large data transfers, private connection"→Direct Connect "remote employees connect to the VPC"→AWS Client VPN
Chapter 3.6

Load balancers

2.2 highly available3.4 network
“

Elastic Load Balancing spreads traffic across healthy targets in several AZs. Application Load Balancer understands HTTP. Network Load Balancer handles raw TCP/UDP at extreme scale with static IPs. Gateway Load Balancer slots third-party firewalls into the path.

ALB · layer 7HTTP/HTTPS/gRPC. Routes by path, host, header or query. Targets: instances, IPs, containers, Lambda. Works with WAF and Cognito login.
NLB · layer 4TCP/UDP/TLS. Millions of requests per second, very low latency, one static or Elastic IP per AZ. Fronts PrivateLink services.
GWLB · layer 3Sends traffic through a fleet of virtual appliances (firewalls, intrusion detection) and back, transparently.
Try it: which load balancer?
Sticky sessions are the best way to keep users logged in.
→
They work, but break scaling and failover. Store session state in ElastiCache or DynamoDB so any instance can serve any user.

Signals

"route /api and /images to different services"→ALB path-based routing "clients must allow-list a fixed IP address"→NLB (Elastic IPs), or Global Accelerator "inspect all traffic with a third-party firewall appliance"→Gateway Load Balancer
Chapter 3.7

Route 53

2.2 highly available3.4 network
“

Route 53 is AWS's DNS. Its routing policies decide which answer each user gets: by weight, by lowest latency, by location, or only from healthy endpoints. Alias records point a domain, even the bare apex, at AWS resources.

Try it: routing policies
Alias vs CNAMEAlias works at the zone apex (example.com) and is free for AWS targets; CNAME can't be used at the apex.
Health checksRoute 53 checks endpoints and stops returning unhealthy ones; failover and multivalue policies rely on this.

Signals

"send 10% of traffic to the new version"→Weighted "active-passive DR to a second Region"→Failover with health checks "EU users must see the EU site for legal reasons"→Geolocation "best performance for global users"→Latency-based
Chapter 3.8

CloudFront and Global Accelerator

3.4 network1.2 workloads4.4 network cost
“

Both use AWS's edge network. CloudFront caches content close to users, for websites, video and APIs. Global Accelerator caches nothing: it gives two static anycast IPs and carries TCP or UDP traffic over the AWS backbone to the healthiest Region.

CloudFrontGlobal Accelerator
DoesCaches and serves content at the edgeRoutes connections to the best regional endpoint
ProtocolsHTTP/HTTPS (and WebSocket)Any TCP or UDP: gaming, VoIP, IoT
AddressesDNS name, changing IPsTwo static anycast IPs
FailoverOrigin groupsInstant, health-based, across Regions
SecurityOrigin access control for S3, signed URLs/cookies, geo-restriction, WAFShield protection, endpoints can stay private
Let users read the S3 bucket directly and put CloudFront in front.
→
Keep the bucket private and allow only CloudFront through origin access control (OAC), so nobody can bypass the CDN.

Signals

"static website, global users, low latency, private bucket"→S3 + CloudFront with OAC "only paying subscribers may download videos"→CloudFront signed URLs or signed cookies "UDP game servers in several Regions, static IPs, fast failover"→Global Accelerator

Lambda

“

Lambda runs your code when an event happens, scales automatically and bills per millisecond. No servers, no idle cost. It suits short, event-driven work; anything over 15 minutes belongs elsewhere.

Chapter 4.6

Other compute: Batch, Beanstalk, hybrid

3.2 compute4.2 compute cost
“

A few services wrap compute for specific jobs. AWS Batch queues and runs batch jobs on the right instances, often Spot. Elastic Beanstalk deploys a web app from code. Outposts, Wavelength and VMware Cloud on AWS cover hybrid and edge needs.

AWS BatchSubmit jobs; Batch provisions EC2 or Fargate (including Spot), runs them in order, scales to zero. For long-running and large-scale batch work.
Elastic BeanstalkUpload code; Beanstalk creates the load balancer, Auto Scaling group and monitoring. You keep access to the resources underneath.
OutpostsAWS infrastructure in your data centre, for low latency to local systems or data that must stay on site.
VMware Cloud on AWSMove vSphere workloads to AWS without re-platforming.
WavelengthCompute inside 5G networks for ultra-low-latency mobile apps.
Serverless Application RepositoryFind and deploy ready-made serverless apps.

Signals

"developers just want to deploy a web app without learning AWS"→Elastic Beanstalk "run thousands of compute jobs that take hours, cost-effectively"→AWS Batch with Spot "migrate VMware workloads quickly, same tools"→VMware Cloud on AWS

SQS

2.1 loosely coupled3.2 compute
“

A queue sits between producers and consumers so neither has to wait for the other. Bursts pile up safely in SQS, consumers work through them at their own pace, and a failed consumer doesn't lose messages.

Try it: a traffic burst
3
Picture it: visibility timeout
  1. A message waits in the queue.
  2. A consumer receives it. SQS hides it from other consumers for the visibility timeout (30 seconds by default).
  3. Success: the consumer deletes the message. Done.
  4. Failure or a crash: the timeout runs out and the message reappears for another try. Set the timeout longer than your processing time to avoid duplicates.
  5. After a set number of failed receives, it moves to a dead-letter queue for investigation, so one bad message can't block the rest.
StandardNearly unlimited throughput; at-least-once delivery; best-effort ordering. Consumers must handle occasional duplicates.
FIFOStrict order within a message group; exactly-once processing with deduplication; lower (but high-throughput-mode capable) rate.

Chapter 8.1

Encryption and KMS

1.3 data
“

KMS holds keys that never leave it in plain form. Services use envelope encryption: a fresh data key encrypts your data, and the KMS key encrypts that data key. Who can use a key is set by its key policy, and every use is logged in CloudTrail.

Picture it: envelope encryption, step by step
  1. A service asks KMS for a data key. KMS returns it twice: once in plain form, once encrypted under your KMS key.
  2. The plaintext data key encrypts the data locally, quickly, any size. Then the plaintext key is thrown away.
  3. The encrypted data key is stored next to the encrypted data.
  4. To decrypt, the service sends the encrypted data key to KMS. KMS checks the key policy and IAM, decrypts it, and logs the call in CloudTrail.
AWS managed vs customer managedAWS managed keys (aws/s3) are automatic. Customer managed keys let you set the key policy, rotation and cross-account use.
RotationAutomatic rotation for customer managed keys keeps old key material so old data still decrypts.
Multi-Region keysThe same key material in several Regions: encrypt in one, decrypt in another without re-encrypting.
CloudHSMYour own single-tenant hardware security modules; you alone control the keys. For strict compliance or custom crypto.

Static stabilityProvision enough in each AZ to survive losing one, without needing to launch more during the failure.
Every layerALB + ASG across AZs, RDS Multi-AZ, NAT per AZ, EFS or S3 for shared data.

Signals

"single EC2 instance runs the app"→ALB + ASG across two or more AZs "no interruption if an AZ fails"→Fault tolerance: full capacity spread over AZs
Chapter 9.2

Disaster recovery

2.2 highly available4.x cost
“

Two numbers drive DR: RPO, how much data you can lose, and RTO, how long you can be down. Four strategies trade cost against those numbers, from cheap backup-and-restore to an always-on second site.

Try it: set the targets
Backup & restoreBack up to another Region; rebuild everything from code and backups on disaster. RPO/RTO hours. Cheapest.
Pilot lightData replicated live; core infrastructure defined but switched off or tiny. Turn it on and scale. Tens of minutes.
Warm standbyA scaled-down but working copy runs all the time; scale it up on failover. Minutes.
Multi-site active-activeFull production in two or more Regions serving traffic. Near-zero RPO and RTO. Most expensive.

Signals

"lowest cost, RTO of a day is acceptable"→Backup and restore "database replicated, minimal servers running until needed"→Pilot light "scaled-down copy always running"→Warm standby "zero downtime, users served from both Regions"→Multi-site active-active

Chapter 10.3

Cost-optimised compute and databases

4.2 compute cost4.3 database cost
“

Pay for what you use and no more. Right-size first, then match the pricing model to the usage pattern: commit for the baseline, Spot for the interruptible, serverless or scale-to-zero for the spiky and the idle.

Expensive habitsm5.4xlarge at 8% CPU, running 24/7 · dev environments on all weekend · On-Demand for a three-year baseline · provisioned DynamoDB sized for the yearly peak · gp2 volumes by default
Cheaper equivalentsRight-size to a smaller Graviton type · stop dev outside office hours (Instance Scheduler) · Savings Plan for the baseline · DynamoDB on-demand or auto scaling · gp3 (cheaper per GB, IOPS separate)
DatabasesReserved instances for steady RDS; Aurora Serverless v2 for spiky; read replicas or caching before scaling up the primary.
Serverless where idleLambda, Fargate, DynamoDB on-demand and Aurora Serverless cost little when traffic is low.
ContainersFargate Spot and EC2 Spot capacity providers for fault-tolerant tasks.
LicencesBring your own licences on Dedicated Hosts, or move to open-source engines (Aurora PostgreSQL).

Signals

"development servers only used 9 to 5 on weekdays"→Schedule start/stop "database busy a few hours a day, idle otherwise"→Aurora Serverless v2 "cut licensing cost of a commercial database"→Migrate to Aurora (DMS + schema conversion)

Exam day strategy

all domains
“

65 questions in 130 minutes is two minutes each. Answer everything (there's no penalty for guessing), flag the slow ones and come back, and let the qualifier in each question decide between options that all work.

Picture it: a time plan
Read the last line firstThe actual ask and qualifier are usually in the final sentence. Then read the scenario for constraints.
Eliminate twoStrike options that break a requirement, are obviously legacy, or need custom code where a managed feature exists.
Count the picksMultiple-response questions say "Choose TWO" or "Choose THREE". Every pick must be correct.
Don't over-think unscored ones15 questions don't count and you can't tell which; a strange one may be one of them.
Overall score countsScoring is compensatory: 720 overall passes, even if one domain is weaker.
Before the daySit the official practice exam on Skill Builder, re-read service FAQs for weak areas, and check the testing setup if sitting online.
