The one idea to carry up every floor

There is no best architecture, only the one that fits your requirements at the lowest cost and complexity. Every building block in this handbook buys something (speed, scale, availability) by giving something up (consistency, simplicity, money). A good design names those trades out loud, backed by rough numbers.

Floor 1 · Foundations

Thinking in systems

What a design is for, how to turn a vague brief into numbers, and a method you can repeat under pressure.

Chapter 1.1

What system design is

“

System design means deciding which parts a system has, where its data lives and how the parts talk, so that it meets its requirements at a cost you can live with. Most systems start as one server and add parts only when a number forces them to.

Picture it: from one server to millions of users
  1. Day one: one server runs the web app and its database together. Cheap and simple, but one failure takes everything down.
  2. Move the database to its own machine, so each can be sized and backed up separately.
  3. Put a load balancer in front of several identical app servers. Now you can add servers and survive losing one.
  4. Add a cache for hot reads and a CDN for images and scripts. Most requests no longer touch the database at all.
  5. Add read replicas: copies of the database that serve reads while the primary takes writes.
  6. Move slow work (emails, thumbnails, reports) onto a queue processed by workers, so users don't wait for it.
  7. When one primary can't take the writes, split the data across shards by key. Each step adds capacity and complexity.
Good design means using every component in the picture.
→
Good design means adding a component only when a requirement or a measured limit justifies its cost and complexity.

What reviewers and interviewers look for

  • Not a "correct" diagram, but clear reasoning: what you assumed, which numbers drove each choice, what you gave up, and what you'd watch in production.
Chapter 1.2

Requirements that shape the design

“

Functional requirements say what the system does. Non-functional requirements say how well: scale, latency, availability, consistency, durability, cost and compliance. The non-functional ones decide the architecture, so pin them to numbers before drawing anything.

Try it: sort the requirements
Picture it: one requirement, one design consequence

Questions to ask first

  • Who are the users, how many, and where? Daily and peak?
  • What are the three most important actions? Read-heavy or write-heavy?
  • How fast must each action feel? What happens if it's slow or down?
  • Can users ever see stale or out-of-order data? Can data ever be lost?
  • How long is data kept? Any legal, privacy or residency rules?
  • What's out of scope for now?

Write the numbers down

  • "Fast" and "scalable" aren't requirements. "p95 under 300 ms at 2,000 requests per second, 99.9% monthly availability" is. Agree them with the product owner before the design review.

Chapter 1.4

Latency numbers to know

“

Memory is fast, disks are slower, networks are slower still, and crossing an ocean is slowest of all. The gaps are factors of a thousand, which is why caching, locality and avoiding round trips dominate design.

Try it: the ladder

Bars on a log scale: each step is roughly ten times the last. Orders of magnitude, rounded; exact values vary by hardware and cloud.

Try it: spend a 200 ms page budget

Tap an operation to add another call (up to three, then back to none).

Count round trips

  • A page that makes ten sequential calls to a service 1 ms away costs 10 ms; to a service in another continent, close to a second. Batch calls, run them in parallel, or move data closer.
Chapter 1.5

A repeatable design method

“

Use the same seven steps every time: clarify requirements, estimate, define the API, sketch the data model, draw the high-level design, deep-dive the risky parts, then wrap up with trade-offs and what you'd improve. The order keeps you from designing the wrong thing well.

Try it: time-box a session
1 · ClarifyUsers, key actions, scale, latency, consistency, out of scope.
2 · EstimateRequests/s, storage, bandwidth, read:write ratio.
3 · APIThe few endpoints or events that matter, with inputs and outputs.
4 · Data modelEntities, keys, access patterns; which store fits.
5 · High levelBoxes and arrows for the main request paths.
6 · Deep diveThe bottleneck or the hard part: scale, consistency, failure.
7 · Wrap upTrade-offs, failure modes, monitoring, what's next.

Drive, but check in

  • In an interview or a review, lead the conversation, but pause after steps 1, 5 and 6 to ask "does this match what you had in mind?". It turns a monologue into a design session.
Chapter 1.6

Trade-offs, not answers

“

Every choice slides along a few dials: consistency or availability, latency or durability, simplicity or flexibility, cost or headroom. Different parts of the same product often sit at different points on the same dial.

Try it: one product, four features
Microservices and NoSQL are what scalable systems use.
→
A well-built monolith on a relational database serves very large products. Split when team size, deploy friction or a measured limit demands it.
# Architecture decision record (ADR): one page per significant choice
ADR = """
# 007: Use a read-through cache for product pages
Status: accepted (2026-11)
Context: product pages are 95% of reads; DB at 70% CPU at peak.
Decision: Redis read-through cache, 5-minute TTL, invalidate on price change.
Consequences: up to 5 minutes stale for non-price fields; new dependency to run.
"""

Record the trade, not just the choice

  • An ADR captures context, decision and consequences. Six months later, it tells people whether the reason still holds.

Floor 2 · Foundations

The edge and APIs

Everything between a user's device and your code: names, connections, caches at the edge, load balancers and the API itself.

Chapter 2.1

From URL to server: DNS and HTTP

“

Before any of your code runs, the browser looks up the name (DNS), opens a connection (TCP), agrees encryption (TLS), then sends the request (HTTP). Each step costs round trips, so the distance between user and server multiplies.

Picture it: one request's journey
  1. The browser checks its own cache, then asks a recursive resolver (often the ISP's or a public one) for shop.example.com.
  2. On a cache miss the resolver asks a root server, then the .com servers, then the domain's authoritative servers. Answers are cached for their TTL.
  3. With the IP address, the browser opens a TCP connection and negotiates TLS. TLS 1.3 needs one round trip; HTTP/3 over QUIC folds both into one.
  4. Now the HTTP request reaches the load balancer and your app. Keeping connections open (keep-alive, pooling) avoids paying setup again.
Try it: what distance costs before the first byte

New connection, DNS already cached, plus 20 ms of server time. Counts round trips only; real numbers add packet loss and processing.

Design implications

  • Low DNS TTLs let you fail over quickly but add lookups; 60–300 s is common for records you may move.
  • Terminate TLS close to users (CDN or edge), reuse connections between services, and avoid chatty protocols across regions.
Chapter 2.2

CDNs and the edge

“

A content delivery network keeps copies of responses in data centres close to users. A hit is answered in milliseconds without touching your servers; a miss travels to your origin once and is cached for the next user nearby.

  • Put every image, video and script behind a CDN from day one; it is usually the cheapest performance and resilience win available.
Chapter 2.3

Load balancers

“

A load balancer spreads requests across healthy servers. Layer 4 balancers route connections by IP and port; layer 7 balancers read HTTP and can route by path, header or cookie. The algorithm matters most when servers or requests are uneven.

Chapter 2.4

API gateways and rate limiting

“

An API gateway is the front door for clients: it authenticates, routes to the right service, enforces limits and records what happened, so each service doesn't reimplement those. Rate limiting protects you from abuse, bugs and noisy neighbours.

Chapter 2.6

Stateless services and scaling out

“

If an app server keeps nothing between requests, any server can handle any request, and you scale by adding copies. State (sessions, uploads, caches) moves to shared stores. Autoscaling then adds and removes copies as traffic changes, but never instantly.

Try it: autoscale through a day

New servers take minutes to boot and warm up. Keep headroom (a lower target) or scale on a schedule for predictable peaks.

Vertical first, horizontal when it counts

Floor 3 · Data

Storing data

How databases lay data out, keep it correct, and which kind to pick for which job.

Chapter 3.1

Picking a data model

“

The same facts can be stored as tables with relationships, as self-contained documents, as key–value pairs, or as a graph of nodes and edges. Choose by how the data will be read and changed, not by fashion.

Try it: one customer's orders, four ways
Time-seriesMetrics and sensor readings: append-only, queried by time range, downsampled with age.
Wide-columnCassandra, Bigtable: huge write volumes, rows keyed for one known query each.
VectorEmbeddings for similarity search, used in RAG and recommendations (Floor 9).

List the access patterns first

  • Write down the top five reads and writes with their frequency ("get a user's last 20 orders, 2,000/s"). The model that serves those cheaply wins; everything else can be slower.
Chapter 3.2

Indexes: B-trees and LSM-trees

“

An index is a sorted structure that finds rows without scanning the whole table. B-trees update pages in place and are fast to read; LSM-trees append writes and merge files in the background, so they absorb heavy write loads. Every index speeds some reads and slows every write.

Picture it: how each finds and stores a key
  1. B-tree read: start at the root page, which says which child holds the key range.
  2. Follow one pointer per level. Each level multiplies coverage by hundreds, so a billion rows need only about four levels.
  3. The leaf page holds the key and a pointer to the row (or the row itself). Writes update this page in place.
  4. LSM write: append to a write-ahead log for durability and insert into an in-memory sorted table (memtable). Very fast.
  5. When the memtable fills, it's flushed to disk as an immutable sorted file (SSTable).
  6. Background compaction merges files and drops overwritten values. Reads may check several files, helped by Bloom filters.
Try it: index lookup vs full scan

Pages of 8 KB holding ~100 rows; B-tree fan-out ~300 keys per page. Reading one random page from SSD ≈ 0.1 ms.

B-treeLSM-tree
WritesRandom page updatesSequential appends; very high throughput
ReadsPredictable, one pathMay check several files
Used byPostgreSQL, MySQL InnoDB, SQL ServerCassandra, RocksDB, ScyllaDB, Bigtable
Add an index for every column, just in case.
→
Each index must be updated on every write and takes memory. Index the columns your frequent queries filter, join and sort on; check with EXPLAIN.

Composite index order matters

  • An index on (customer_id, created_at) serves "this customer's recent orders" perfectly, and is useless for "all orders yesterday". Order columns by equality filters first, then range or sort.
Chapter 3.3

Transactions and isolation

“

A transaction groups changes so they all happen or none do (atomicity) and survive crashes (durability). Isolation decides what concurrent transactions see of each other. Weaker isolation is faster but allows anomalies, such as two updates where one silently overwrites the other.

# Optimistic concurrency: no locks held; retry if someone else changed the row
def top_up(account_id, amount):
    for _ in range(3):
        bal, ver = db.one("SELECT balance, version FROM accounts WHERE id=%s", account_id)
        n = db.exec("UPDATE accounts SET balance=%s, version=version+1 WHERE id=%s AND version=%s",
                    bal + amount, account_id, ver)
        if n == 1:
            return                  # our version was still current
    raise ConflictError("too much contention, try later")

Know your default

  • Most apps run at read committed without realising it. For counters and balances, use atomic updates, row locks or version checks; reach for serializable where rules span several rows (write skew).
Chapter 3.4

Object, file and block storage

“

Databases hold structured records; big files belong elsewhere. Object storage (such as S3) stores whole files by key with huge durability and low cost. Block storage is a raw disk for one server; file storage is a shared folder. Store the file in object storage and its metadata in your database.

Picture it: uploads that skip your servers
  1. The client asks your API for permission to upload a photo.
  2. The API records pending metadata and returns a short-lived pre-signed URL for one object key.
  3. The client uploads the bytes straight to object storage. Your servers never carry the file.
  4. Object storage emits an event; a worker makes thumbnails and marks the record ready. A CDN serves downloads.
Try it: storage classes for one year

Relative prices modelled on typical public-cloud ratios: standard 1.0, infrequent access ~0.55 plus a retrieval fee, archive ~0.15 plus a bigger fee and hours to restore. Check your provider's price list.

Lifecycle rules do the work

  • Move objects to cheaper classes automatically as they age, and delete what retention rules allow. Keep versioning on for anything you can't afford to lose to a bad deploy.
Chapter 3.5

Search and analytics stores

“

A transactional database is tuned to read and change a few rows fast. Full-text search needs an inverted index (word → documents). Analytics over billions of rows needs column storage, which reads only the columns a query uses. Copy data into these stores rather than forcing one database to do everything.

Try it: an inverted index

Scaling data

When one database server isn't enough: caches, copies, splits, and the consistency you give up for them.

Chapter 4.1

Caching

“

A cache keeps recently or frequently used results in fast memory so most reads skip the slow store. Because real traffic is skewed (a few items get most requests), a small cache often absorbs most reads. The hard parts are keeping it fresh and surviving when it's empty.

Picture it: cache-aside
  1. Read: the app checks the cache first. A hit returns in about a millisecond.
  2. Miss: the app reads from the database, then writes the value into the cache with a TTL for next time.
  3. Write: the app updates the database, then deletes the cached key so the next read fetches the new value.
Try it: how big must the cache be?
0hit ratio
0of reads still reach the database

One million items with Zipf-distributed popularity; the cache holds the most popular ones. Skew 1 is typical of web content.

Write-throughWrite cache and DB together: fresh, slower writes.
Write-backWrite cache, flush later: fast, risks loss.
EvictionLRU (least recent) or LFU (least frequent) plus TTLs.
StampedeA hot key expires and thousands of requests hit the DB at once. Use request coalescing, early refresh and TTL jitter.
import random
def get_product(pid):
    key = f"product:{pid}"
    if (hit := cache.get(key)) is not None:
        return hit
    with lock(f"fill:{key}", timeout=2):            # one request refills; others wait briefly
        if (hit := cache.get(key)) is not None:
            return hit
        row = db.one("SELECT * FROM products WHERE id=%s", pid)
        cache.set(key, row, ttl=300 + random.randint(0, 60))   # jitter spreads expiries
        return row

def update_price(pid, price):
    db.exec("UPDATE products SET price=%s WHERE id=%s", price, pid)
    cache.delete(f"product:{pid}")                  # invalidate after the write

Decide how stale is acceptable

  • State a staleness budget per data type ("prices: seconds, reviews: minutes"). Plan for a cold cache: can the database survive if the cache is flushed at peak?
Chapter 4.2

Replication

“

Replication keeps copies of the same data on several machines, for availability (survive a failure), read capacity and locality. With one leader, writes go to the leader and stream to followers, usually asynchronously, so followers can lag behind.

Try it: read your own write from a replica
Try it: leaderless quorums (N, W, R)
Single leaderSimple, consistent writes; failover needed when the leader dies. PostgreSQL, MySQL.
Multi-leaderWrites in several regions; must resolve conflicts. Collaborative and offline apps.
LeaderlessWrite to W of N, read from R of N. Dynamo-style: Cassandra, Riak.

Route reads deliberately

  • Send a user's reads to the leader for a short time after they write (read-your-writes), or track the replication position they've seen. Everyone else can read from replicas.
Chapter 4.3

Partitioning and sharding

“

When one machine can't hold the data or take the writes, split the data into partitions (shards) by a key, each on its own servers. The shard key decides everything: a good one spreads load evenly and keeps each query on one shard; a bad one creates hot spots and scatter-gather queries.

Try it: choose a shard key for orders
Range partitioningKeeps neighbours together (good for range scans), but the newest range is often hot.
Hash partitioningSpreads evenly; range queries must ask every shard.
Secondary indexesLocal per shard (writes cheap, reads scatter) or global (reads targeted, writes cross shards).

Shard late, pick the key early

  • Sharding adds cross-shard queries, rebalancing and operational work; postpone it with bigger machines, replicas and caches. But choose IDs and keys now that would shard cleanly later.
Chapter 4.4

Consistent hashing

“

With hash(key) mod N, adding one server moves almost every key. Consistent hashing places servers and keys on a ring; each key belongs to the next server clockwise, so adding a server only takes keys from its neighbour. Virtual nodes give each server many small slices to even out the load.

Try it: add a server

2,000 keys. Keys moved = keys whose server changes when one more server joins.

Where you'll meet it

  • Distributed caches (client-side sharding across Memcached), Dynamo-style databases, and load balancers that need sticky routing. Rendezvous (highest-random-weight) hashing is a simpler alternative with the same property.
Chapter 4.5

Consistency models and CAP

“

When the network splits replicas apart, a system must choose: refuse some requests to stay consistent, or keep answering and let the copies diverge until the split heals. That's the CAP theorem. When there's no split, the trade is latency against consistency (PACELC).

  2. The network cuts replica C off from A and B.

Chapter 4.6

Hot keys and skew

“

Even with perfect hashing, one key can be far more popular than the rest: a celebrity's profile, a flash-sale product, a viral post. All its traffic lands on one shard. Spread the hot key across several sub-keys, cache it close to the callers, or batch its writes.

Try it: one viral item on ten shards

Each shard can take 15% of total traffic. Sub-keys (item:42#0 … item:42#n) land on different shards.

import random
N = 16                                    # sub-counters for one hot key
def like(post_id):
    redis.incr(f"likes:{post_id}:{random.randrange(N)}")     # writes spread over 16 keys

def like_count(post_id):
    return sum(int(redis.get(f"likes:{post_id}:{i}") or 0) for i in range(N))  # reads gather

Detect, then treat

  • Track top keys per shard. Treat known-hot entities specially (celebrities, sale items) and keep a small in-process cache for the hottest reads.

Async and events

Decouple work in time with queues, logs and streams, and keep it correct when messages repeat.

Chapter 5.1

Why go asynchronous

“

When one request calls service after service synchronously, latencies add up and availabilities multiply down: any slow or failed link fails the user. Put work that doesn't need to finish before the reply onto a queue, and the user waits only for what matters.

Try it: a chain of services

Each service takes 40 ms. Async: the API saves the order, enqueues the rest and replies; downstream services catch up from the queue, even after an outage.

Try it: a queue absorbs a burst
━ jobs arriving/s━ jobs waiting (thousands)

Ask "must this finish before we reply?"

  • Emails, thumbnails, search indexing, analytics and most notifications don't. Payment authorisation usually does. Make that split explicit for each request path.
Chapter 5.2

Queues and pub/sub

“

A work queue hands each message to exactly one of several competing workers, which spreads the load. Publish/subscribe copies each message to every subscriber, so many independent services can react to one event.

Picture it: two shapes
AcknowledgeA worker deletes (acks) a message only after finishing. If it crashes, the message reappears after a visibility timeout.
Dead-letter queueAfter N failed attempts, park the message for inspection instead of retrying forever.
Back-pressureWatch queue depth and age of the oldest message; scale workers on them.
ProductsQueues: SQS, RabbitMQ. Pub/sub: SNS, Google Pub/Sub, Kafka topics.

Queues hide problems until they don't

  • Alert on the age of the oldest message, not just the count. A queue that grows slowly for days is a capacity incident in waiting.
Chapter 5.3

Logs and Kafka

“

A log-based broker such as Kafka keeps messages in an append-only, partitioned log for days or forever, instead of deleting them once read. Each consumer group tracks its own position (offset), so many systems can read the same events independently and replay history.

Try it: partitions and a consumer group
OrderingGuaranteed only within a partition. Key messages by entity (order ID) so each entity's events stay in order.
ParallelismA group can use at most one consumer per partition; choose partitions for future scale.
ReplayReset an offset to reprocess after a bug, or let a new service read history.

Queue or log?

  • A queue when each job is done once and forgotten. A log when several consumers need the same events, order matters per key, or you want to replay. Many systems use both.
Chapter 5.4

Delivery guarantees and idempotency

“

Networks and crashes force a choice: risk losing a message (at-most-once) or risk processing it twice (at-least-once). Most systems pick at-least-once and make consumers idempotent, so processing a message twice has the same effect as once. That's "exactly-once" in practice.

Picture it: the crash that causes a duplicate
  1. The worker receives "charge order 71 £40" from the queue.
  2. It charges the card successfully.
  3. It crashes before acknowledging the message.
  4. The visibility timeout expires and the message is delivered again, to another worker, which charges again. Unless it checks an idempotency key first.
Try it: a day of messages
0customers charged twice (of 1M orders)
def handle(msg):
    with db.transaction():
        # unique constraint on message_id makes the second attempt fail here
        inserted = db.exec("INSERT INTO processed(message_id) VALUES (%s) ON CONFLICT DO NOTHING", msg.id)
        if inserted == 0:
            return                       # already done: ack and move on
        db.exec("UPDATE accounts SET balance = balance - %s WHERE id = %s", msg.amount, msg.account)
    queue.ack(msg)                       # ack after commit; a crash here just redelivers harmlessly

Idempotency keys end to end

  • Have clients send an idempotency key on create and charge requests, store it with the result, and return the stored result on a retry. Pass the same key to payment providers, which support it.

Batch jobs process a bounded pile of data on a schedule; stream processors handle events continuously as they arrive. Streams group events into time windows, and must decide what to do when an event arrives late, after its window seemed complete.

Chapter 5.6

Event patterns: outbox, saga, CQRS

“

Writing to your database and publishing an event are two separate actions; if one fails, they disagree. The outbox pattern writes the event into the database in the same transaction, then relays it. Sagas run a business process across services as steps with compensating actions instead of one giant transaction.

Picture it: an order saga with a failed payment
  1. The order service saves the order as PENDING and, in the same transaction, writes an OrderCreated row to its outbox table.
  2. A relay publishes outbox rows to the broker. The inventory service reserves stock and emits StockReserved.
  3. The payment service tries to charge the card and fails: PaymentFailed.
  4. Compensation: inventory releases the reserved stock (undoing step 2) and the order is marked CANCELLED. No distributed lock was ever held.
ChoreographyServices react to each other's events. Loosely coupled; the flow is hard to see.
OrchestrationA coordinator (e.g. Temporal, Step Functions) calls each step. Clear flow, one more component.
CQRSSeparate models for writes and reads; read models are built from events and can be shaped per screen.
Event sourcingStore the events themselves as the source of truth; state is a fold over them. Full audit, harder evolution.
def place_order(cart):
    with db.transaction():                        # one local transaction, both rows or neither
        order_id = db.insert("orders", status="PENDING", **cart)
        db.insert("outbox", topic="orders", key=order_id,
                  payload=json.dumps({"type": "OrderCreated", "order_id": order_id, **cart}))
    return order_id
# A relay (or Debezium reading the DB log) publishes outbox rows, then marks them sent.

Design the compensations up front

  • For each saga step, write down its undo and what the user sees meanwhile ("Payment pending"). Some steps can't be undone (an email was sent), so order steps to put those last.

Distributed systems realities

Networks drop, clocks drift and machines pause. The tools that keep many machines agreeing anyway.

Chapter 6.1

What goes wrong

“

In a distributed system, parts fail while the rest keeps running. Messages are lost or delayed, machines pause, disks die, clocks drift. Worse, a caller often can't tell whether the other side crashed, is slow, or did the work and the reply got lost.

Try it: failure at scale is routine
0failures per day
0between failures on average
The fallacies of distributed computing

Design for partial failure

  • For every arrow in your diagram, ask: what if this call is slow, fails, or succeeds but the reply is lost? The answers become timeouts, retries, idempotency and fallbacks.
  • Watch for gray failures: a node that passes health checks but serves errors or is very slow.
Chapter 6.2

Timeouts, retries and backoff

“

Every remote call needs a timeout, or a slow dependency will tie up all your threads. Retries recover from brief failures, but naive retries multiply load exactly when a system is struggling. Back off exponentially, add random jitter, and cap retries with a budget.

Try it: 1,000 clients retry after an outage

All clients fail at time 0 and retry up to 5 times; the service can handle 250 requests per 100 ms (dashed line). Backoff starts at 0.5 s and doubles.

Try it: retries at every layer
0× requests reaching the bottom service when it fails
import random, time

def call_with_retries(fn, attempts=4, base=0.1, cap=5.0):
    for n in range(attempts):
        try:
            return fn(timeout=0.8)                  # every call gets a timeout
        except (Timeout, Unavailable):
            if n == attempts - 1:
                raise
            time.sleep(random.uniform(0, min(cap, base * 2 ** n)))   # full jitter

Retry in one place

  • Retry at the edge (or one chosen layer), not at every hop. Only retry idempotent operations or ones with idempotency keys, and set timeouts from measured p99 latency, not guesses.
Chapter 6.3

Time, clocks and ordering

“

Each machine's clock drifts, and synchronisation (NTP) only keeps them within milliseconds, sometimes worse. So "the latest timestamp wins" can throw away the write that really happened last. Logical clocks order events by cause instead of by wall time.

Try it: last-write-wins with clock skew
Lamport clockA counter: increment on each event, take max(own, received) + 1 on each message. If A caused B, A's number is smaller.
Vector clockOne counter per node; can tell "happened before" from "concurrent", so conflicts can be detected.
Hybrid / TrueTimeHLCs mix wall time with a logical counter (CockroachDB); Spanner waits out a bounded clock uncertainty.

Don't order with wall clocks across machines

  • Use a single sequencer (a database sequence, a Kafka partition offset), version numbers, or logical clocks. Keep wall-clock timestamps for display and rough analytics.
Chapter 6.4

Consensus and leader election

“

Consensus lets a group of machines agree on a value, or a sequence of values, even when some fail. Raft does it by electing one leader per term, which appends entries to a log and commits each once a majority has stored it. With 2f + 1 nodes, it survives f failures.

Picture it: Raft in four steps
  1. Five nodes. Node 1 is leader for term 3 and sends regular heartbeats.
  2. Node 1 crashes. Node 3 hears no heartbeat before its randomised timeout, becomes a candidate for term 4 and asks for votes.
  3. Nodes 2, 4 and 5 grant their votes. With its own vote node 3 has 4 of 5, more than the majority of 3, so it becomes leader for term 4.
  4. A client write goes to node 3, which appends it and replicates. Once a majority has it on disk, it's committed and applied, even with node 1 still down.
Try it: cluster size

Use it, don't build it

  • Rely on etcd, ZooKeeper, Consul or a database with built-in consensus for leader election, configuration and locks. Run 3 or 5 nodes across availability zones; more nodes means slower writes.
Chapter 6.5

Unique IDs at scale

“

One database's auto-increment can't serve many shards or regions. Random UUIDs need no coordination but scatter inserts across an index. Time-ordered IDs (Snowflake, UUIDv7, ULID) are unique without coordination and still sort roughly by creation time.

Try it: design a Snowflake-style 64-bit ID

  • It needs no coordination, sorts by time and fits standard UUID columns. Choose 64-bit Snowflake IDs when storage per row really matters, and never expose sequential IDs where guessing them leaks data.
Chapter 6.6

Distributed locks and leases

“

A distributed lock lets one worker at a time do something. It must expire (a lease), or a crashed holder blocks everyone forever. But a holder can pause past its lease without knowing, so two workers think they own it. Fencing tokens let the storage reject the stale one.

Picture it: the pause that breaks a lock
  1. Worker A takes the lock with a 10-second lease and gets fencing token 33.
  2. A pauses (a long garbage-collection pause or a VM freeze) for 15 seconds. The lease expires.
  3. Worker B takes the lock: token 34. It writes to storage with token 34.
  4. A wakes up, still believing it holds the lock, and writes with token 33. Storage has already seen 34, so it rejects 33. Without tokens, A would overwrite B's work.
# Storage side: accept a write only if its token is the newest seen for this resource
def write(resource, data, token):
    n = db.exec("""UPDATE resources SET data=%s, last_token=%s
                   WHERE id=%s AND last_token < %s""", data, token, resource, token)
    if n == 0:
        raise StaleLockError("a newer lock holder has written")

Often you don't need a lock

  • A unique constraint, a conditional update, a single-partition queue, or one leader per shard usually does the job more safely. If you do lock, use a consensus-backed store and fencing tokens for anything that must be correct.

Chapter 7.1

SLIs, SLOs and error budgets

“

An SLI is a measurement users would care about, such as the share of requests that succeed within 300 ms. An SLO is the target for it, say 99.9% over 30 days. The gap between 100% and the SLO is the error budget: failures you can spend on releases and experiments before reliability work takes priority.

Try it: what a target allows
0allowed downtime per 30 days
0per year

Pick SLIs from the user's viewSuccess rate and latency at the load balancer or client, not CPU or memory.

Each nine costs moreGoing from 99.9% to 99.99% usually means multi-zone or multi-region, automated failover and slower, safer releases.

Agree the policy, not just the number

Chapter 7.2

Redundancy, failover and multi-region

“

Components in a chain multiply their availabilities down; identical copies in parallel multiply their failure chances down. Remove single points of failure tier by tier, then decide how much of a whole region's loss you need to survive, measured by RTO (how long to recover) and RPO (how much data you may lose).

Try it: three tiers, how many copies?

Assumes failures are independent and failover is instant, which real systems only approximate: shared dependencies and bad deploys fail many copies at once.

Chapter 7.3

Resilience patterns

“

A slow dependency is more dangerous than a dead one: requests pile up waiting, threads run out, and the failure spreads upstream. Timeouts bound the wait, circuit breakers stop calling a failing dependency, bulkheads give each dependency its own pool, and load shedding drops excess work early.

Try it: a dependency slows down

400 requests/s each call this dependency; the server has 200 worker threads. Threads busy = requests/s × time each waits (Little's law).

Picture it: a circuit breaker
  1. Closed: calls flow normally while the breaker counts failures over a rolling window.
  2. Too many failures: the breaker opens. Calls fail immediately (or use a fallback) without touching the dependency, giving it room to recover.
  3. After a cool-down it goes half-open and lets a few trial calls through.
  4. If they succeed it closes again; if they fail it reopens for another cool-down.
FallbacksCached results, defaults, a simpler path ("recommendations unavailable").
BulkheadsSeparate pools per dependency so one can't exhaust everything.
Load sheddingReject early with 503 when queues are deep; prioritise important traffic.

Decide what degrades

  • List each dependency as critical (fail the request) or optional (degrade). Most product pages have more optional parts than teams assume.
Chapter 7.4

Observability

“

Metrics tell you something is wrong, traces show where in the request path, and logs explain why. Measure percentiles, not averages: when a page fans out to many services, a large share of pages hit some service's slow tail.

Try it: tail latency at scale
Picture it: a trace
Four golden signalsLatency, traffic, errors, saturation for every service.

OpenTelemetryOne standard for metrics, logs and traces; propagate trace IDs through queues too.

Instrument before launch

  • A design isn't finished without its dashboards and alerts: name the SLIs, the saturation signals for each bottleneck, and the trace attributes you'll need during an incident.
Chapter 7.5

Deploying safely

“

Most outages follow a change. Ship small changes, expose them to a little traffic first (canary), watch the signals, and keep rollback fast. Separate deploying code from releasing features with flags, and change database schemas in backwards-compatible steps.

Try it: canary blast radius
0requests hit the bug
0of a 99.9% monthly error budget

A bad release fails 30% of its requests; the service handles 2,000 requests/s.

Picture it: expand and contract a schema
  1. Expand: add the new column (full_name) alongside the old ones. Old code ignores it.
  2. Deploy code that writes both old and new columns.
  3. Backfill the new column for existing rows, in batches.
  4. Switch reads to the new column. Old columns still written, so rollback is safe.
  5. Stop writing the old columns.
  6. Contract: drop the old columns once nothing reads them. Every step could be rolled back alone.

Make rollback boring

  • Automate canary analysis and rollback, keep the previous version warm (blue/green), and never couple a deploy to an irreversible migration.

Chapter 8.1 · Case study

URL shortener

“

Turn a long URL into a short code and redirect anyone who visits it. Writes are rare, reads are a hundred times more common and must be fast. The core design question is how to generate short, unique codes without a bottleneck.

Functional
  • Create a short link (optional custom alias, expiry)
  • Redirect short → long
  • Basic click analytics
Non-functional
  • 100M new links a month; 100 reads per write
  • Redirect p99 < 50 ms; 99.99% available
  • Codes unguessable enough to deter enumeration
Try it: how long must the code be?
Picture it: the design
  1. Create: the API asks the ID service for the next number and encodes it in base62 (e.g. 125 → "21"). No collision checks needed.
  2. The ID service hands each API server a block of 1,000 numbers at a time, so it's rarely called and not a bottleneck.
  3. The mapping (code → long URL) goes into a key–value store, sharded by code.
  4. Redirect: look up the code in the cache (most clicks are on a few hot links), then the store; reply 302 to the long URL.
  5. Each click is published to a queue; analytics workers aggregate counts without slowing the redirect.
ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"
def encode(n: int) -> str:
    s = ""
    while n:
        n, r = divmod(n, 62); s = ALPHABET[r] + s
    return s or "0"
# POST /v1/links {"url": "...", "alias": null, "expires": null} → {"code": "aZ3k9Qx"}
# GET /{code} → 302 Location:

The point of this exercise

  • It tests estimation, ID generation, caching a read-heavy path and keeping analytics off the hot path. Keep the core tiny and say so.
Chapter 8.2 · Case study

Rate limiter

“

Limit each API key to N requests per minute across fifty gateway servers. One server counting alone can't see the others' traffic, so the counters must be shared, fast and atomic, and the limiter must not take the API down when it fails.

Functional
  • Per key, per endpoint and per IP rules
  • Return 429 with Retry-After when over the limit
  • Rules editable without redeploying
Non-functional
  • Adds under 1–2 ms at p99
  • Accurate within a few per cent
  • The API keeps serving if the limiter fails
Try it: size the counter store
Picture it: the design
  1. Every gateway runs limiter middleware that loads rules (from a config service) into memory.
  2. For each request it runs one atomic script in Redis: refill and take a token for this key. One round trip, ~1 ms.
  3. Allowed: forward to the backend. Denied: return 429 with Retry-After and quota headers.
  4. If Redis is slow or down, fail open (allow) and fall back to a rough per-gateway local limit, so a limiter outage doesn't become an API outage.
TOKEN_BUCKET = """
local tokens, ts = unpack(redis.call('HMGET', KEYS[1], 'tokens', 'ts'))
local cap, rate, now = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
tokens = math.min(cap, (tonumber(tokens) or cap) + (now - (tonumber(ts) or now)) * rate)
local ok = tokens >= 1
if ok then tokens = tokens - 1 end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('EXPIRE', KEYS[1], math.ceil(cap / rate) * 2)
return ok and 1 or 0
"""
allowed = redis.eval(TOKEN_BUCKET, 1, f"rl:{api_key}", 100, 100 / 60, time.time())  # atomic

The point of this exercise

  • Shared state on the hot path: atomicity, latency budget, hot keys and graceful failure. Mention the algorithm choice briefly (Floor 2) and spend time on those.
Chapter 8.3 · Case study

News feed

“

Show each user recent posts from the people they follow. You can build feeds when someone posts (fan-out on write: fast reads, expensive for accounts with millions of followers) or when someone reads (fan-out on read: cheap writes, slow reads). Real systems mix both.

Functional
  • Post text and media
  • Home feed of followed accounts, newest or ranked
  • Infinite scroll
Non-functional
  • 300M daily users, 2 posts and 20 feed loads each a day
  • Feed load p99 < 200 ms
  • A post can take seconds to appear in feeds
Try it: where to draw the celebrity line

Illustrative population of 300M accounts: most have a few hundred followers; 1,000 have tens of millions and post several times a day. A typical user follows ~50 accounts above 10k followers.

Picture it: the hybrid design
  1. A user posts; the post service stores it and publishes PostCreated.
  2. Fan-out workers look up the author's followers and push the post ID onto each follower's feed list in a cache (Redis), trimmed to the latest ~800.
  3. Authors over the celebrity threshold are skipped by fan-out.
  4. Feed read: take the precomputed list, merge in recent posts from the celebrities this user follows, rank, then hydrate post details from the post cache.

The point of this exercise

  • Read vs write amplification, skewed data (celebrities), caching precomputed results and async pipelines. Quantify the fan-out before choosing.
Chapter 8.4 · Case study

Chat and presence

“

Deliver messages between users in real time, in order, without losing any, and show who's online. Clients hold long-lived connections to gateway servers, so the system must know which gateway each user is on, and store messages for users who are offline.

Functional
  • One-to-one and group chats (up to 500 members)
  • Delivered and read receipts
  • Online status, message history on any device
Non-functional
  • 50M concurrent connections at peak
  • Delivery under 300 ms when online
  • No lost messages; order kept per chat
Try it: size the connection tier
Picture it: sending a message
  1. Alice's app holds a WebSocket to gateway 1 and sends a message with a client-generated ID (for de-duplication).
  2. The chat service assigns a sequence number within the conversation and stores the message (partitioned by conversation ID). Only then is Alice told "sent".
  3. It looks up Bob's gateway in the session registry and forwards the message; gateway 7 pushes it over Bob's socket. Bob's app acks: "delivered".
  4. If Bob is offline, a push notification goes out instead; when he reconnects his app asks for everything after the last sequence number it has.

Chapter 8.5 · Case study

Video streaming

“

An uploaded video is transcoded into several resolutions, cut into short segments and served from CDNs. Players switch quality segment by segment to match the viewer's bandwidth. The challenges are processing throughput, storage cost and, above all, egress bandwidth.

Functional
  • Upload, process, publish
  • Watch on any device and network
  • Resume, seek, thumbnails
Non-functional
  • Start playing in under 2 s; rare rebuffering
  • Millions of concurrent viewers
  • Uploads processed within minutes
Try it: adaptive bitrate
Try it: egress at peak

Average 5 Mb/s per viewer.

Picture it: upload to playback
  1. The creator uploads the original straight to object storage with a pre-signed, resumable multipart upload.
  2. A job splits the video into chunks and transcodes them in parallel into a bitrate ladder (240p to 4K), then packages HLS/DASH segments and a manifest.
  3. Segments land in object storage; metadata (status, renditions) goes to the database and the video is published.
  4. Viewers fetch the manifest and segments from the nearest CDN edge; the player picks a rendition per segment from measured bandwidth.

The point of this exercise

  • Pipelines and parallel processing, object storage, CDN economics and client-side adaptation. Popular videos dominate traffic, so tier storage and pre-warm CDNs for launches.
Chapter 8.6 · Case study

Ride-hailing and location

“

Drivers send their position every few seconds; riders need the nearest available drivers in milliseconds. The heart of the design is a geospatial index that is cheap to update constantly and fast to query by area, plus a matching flow that never assigns one driver twice.

Functional
  • Drivers share location and availability
  • Riders see nearby cars and request a ride
  • Match, track the trip, pay
Non-functional
  • 1M active drivers updating every 4 s
  • Nearby search p99 < 100 ms
  • A driver is never double-booked
Try it: geohash cells
Picture it: request to match
  1. Driver apps send location every 4 seconds to the location service, which updates an in-memory geospatial index (e.g. Redis GEO or H3 cells), sharded by region.
  2. A rider requests a ride; the matching service queries the index for available drivers in nearby cells and ranks them by ETA.
  3. It offers the trip to the best driver with a conditional update ("available → offered", only if still available), so two riders can't get the same driver.
  4. On accept, the trip service creates the trip (a state machine: requested, accepted, arrived, in progress, completed) and both apps get live updates.

The point of this exercise

  • High-frequency writes of short-lived data (keep it in memory, don't fsync every ping), spatial indexing, regional sharding, and correctness for the one write that matters: the match.

Chapter 9.1 · Case study

Payment system

“

Take a customer's money through an external payment provider and record it so the books always balance. Speed matters less than correctness: every step must be safe to retry, every state change recorded, and every penny reconciled against the provider's own records.

Functional
  • Charge a card or wallet at checkout
  • Refunds, payouts to sellers, fees
  • Statements and reports
Non-functional
  • Never charge twice, never lose a payment
  • Full audit trail; PCI DSS and data protection
  • Modest volume (hundreds per second) but high value
Picture it: one payment, end to end
  1. Checkout creates a payment intent with an idempotency key. A retry with the same key returns the same intent instead of creating another.
  2. The card details go from the customer's browser straight to the provider's hosted fields; you receive a token, which keeps raw card numbers (and most PCI scope) out of your systems.
  3. The payment service calls the provider with the token and the same idempotency key, and records the state: PENDING → AUTHORISED or FAILED.
  4. The provider later confirms by webhook (signed, possibly repeated or out of order). The service updates the state idempotently and writes balanced ledger entries.
  5. Each night a reconciliation job compares the ledger with the provider's settlement file and flags any mismatch for a person to resolve.
Try it: a double-entry ledger
AccountBalance

The point of this exercise

  • Idempotency end to end, explicit state machines, append-only records and reconciliation. Say what happens on every timeout and duplicate.
Chapter 9.2 · Case study

File sync and storage

“

Keep a folder in sync across a user's devices and collaborators. Split files into chunks identified by their content hash, so an edit uploads only the chunks that changed and identical chunks are stored once. Metadata says which chunks make up which version of which file.

Functional
  • Upload, download, sync across devices
  • Share folders; version history
  • Work offline, sync later
Non-functional
  • 500M users, files up to 50 GB
  • Changes appear on other devices within seconds
  • Never lose a file; resolve conflicts visibly
Try it: edit a big file

4 MB chunks; the edit touches one contiguous region. Content-defined chunking (boundaries chosen by content, not position) also copes with inserts that shift everything after them.

Picture it: syncing an edit
  1. The desktop client notices a change, re-chunks the file and hashes each chunk.
  2. It asks the metadata service which hashes are already stored, then uploads only the missing chunks to block storage.
  3. It commits a new file version (list of chunk hashes) to the metadata database, conditional on the version it started from.
  4. The notification service tells the user's other devices (long poll or WebSocket); they fetch the new chunk list and download only what they lack.

The point of this exercise

  • Separating metadata from blobs, content addressing and de-duplication, change notification, and conflicts: if the commit's base version is stale, keep both copies ("conflicted copy") rather than overwrite.
Chapter 9.3 · Case study

Search autocomplete

“

Suggest the most popular completions for what the user has typed, in under 100 ms, on every keystroke. The trick is to do the heavy work offline: aggregate query logs, build a prefix tree with each node's top suggestions precomputed, and serve it from memory.

Functional
  • Top 5 suggestions per prefix
  • Ranked by popularity (and freshness)
  • Filter offensive terms
Non-functional
  • 10M daily users, ~10 keystrokes per search
  • p99 under 100 ms end to end
  • Trends visible within an hour
Try it: type a prefix
Picture it: offline build, online serve
ClientDebounce keystrokes (~100 ms), cache responses for prefixes already seen, cancel stale requests.
ServingTrie shards by prefix range, replicated; responses cacheable at the CDN for popular prefixes.
FreshnessRebuild hourly; blend in a small streaming "trending" layer for breaking topics.

The point of this exercise

  • Moving work from read time to build time, data structures with precomputed answers, and client-side tricks that cut traffic by half or more.
Chapter 9.4 · Case study

Notification system

“

Many services need to tell users things, by push, SMS, email or in-app. A central notification service applies user preferences, de-duplicates and rate-limits, renders templates, and sends through each provider with retries, so product teams just publish "what happened".

Functional
  • Push (APNs, FCM), SMS, email, in-app
  • Preferences, quiet hours, unsubscribe
  • Transactional and marketing campaigns
Non-functional
  • Transactional: delivered within seconds
  • Campaigns: 20M messages without starving transactional
  • No duplicates; respect provider limits
Try it: send a campaign
Picture it: from event to device
  1. Services publish events ("order shipped", "campaign 42") to the notification service's API or topic.
  2. It checks preferences and quiet hours, de-duplicates (same event and user within a window), and renders the template in the user's language.
  3. Messages go onto per-channel, per-priority queues, so a marketing blast never delays a password reset.
  4. Channel workers send via providers within their rate limits, retry with backoff, record delivery status and handle bounces and invalid tokens.

The point of this exercise

  • Fan-out with priorities, third-party limits and failures, idempotency, and user control. Mention unsubscribe and consent: they're legal requirements, not features.
Chapter 9.5 · Case study

An LLM chat assistant

“

A chat assistant is a normal web app wrapped around an unusual dependency: a model call that takes seconds, streams tokens, costs money per token and sometimes misbehaves. Design for streaming, context management, a model gateway with fallbacks, safety checks and cost control.

Functional
  • Multi-turn chat with history
  • Streaming answers; stop generating
  • File uploads, tools such as web search
Non-functional
  • First token in under 1 s; smooth streaming
  • Survive a model provider outage
  • Predictable cost per user
Try it: tokens and cost

Illustrative prices: $3 per million input tokens, $15 per million output, cached input at 10% of the input price; 400 output tokens per reply. Use your provider's real prices.

Picture it: one message
  1. The client sends a message; the chat service loads the conversation and builds the context: system prompt, recent turns, a summary of older ones, retrieved files.
  2. Input safety checks run (abuse, prompt injection in uploaded content), and the request goes to the model gateway.
  3. The gateway applies per-user rate and spend limits, picks a model, and falls back to another provider on errors or timeouts.
  4. Tokens stream back to the browser over server-sent events while the service accumulates the reply.
  5. When done, the reply is stored, usage is metered, and traces go to observability and evaluation pipelines.

The point of this exercise

  • Long-running streaming requests, context as a budget, a gateway for resilience and cost, and evaluation as part of the system. For serving models yourself, see the Inference Engineering Handbook.
Chapter 9.6 · Case study

RAG and agent platforms

“

Retrieval-augmented generation answers from your own documents: ingest and index them ahead of time, retrieve the most relevant passages per question, and have the model answer with citations. An agent platform adds tools the model can call, which raises the stakes: permissions, sandboxes, approvals and traces become core design.

Functional
  • Ingest documents from many sources
  • Answer with citations; respect document permissions
  • Agents call tools (search, tickets, code) with approval
Non-functional
  • Answers grounded; measured with evals
  • Users never see documents they can't access
  • Every agent action traceable and reversible where possible
Try it: the retrieval budget
Picture it: ingest, retrieve, act
  1. Ingestion: connectors pull documents with their access lists; a pipeline parses, chunks, embeds and indexes them (vectors plus keywords), re-running on change.
  2. Question: retrieve by hybrid search (keyword + vector), filtered to what this user may see, then rerank the candidates.
  3. Generate: the model answers from the retrieved passages and cites them; answers without support are flagged.
  4. Agents: the model may call tools from a registry. Each tool runs with the user's permissions, risky ones need human approval, and code runs in a sandbox.
  5. Every step is traced and sampled into evaluations for retrieval quality, groundedness and tool safety.
With long-context models, retrieval is no longer needed.
→
Corpora are far larger than any context window, permissions must be enforced per user, and stuffing context costs money and latency. Retrieval remains the default.

The point of this exercise

  • Data pipelines, permission-aware search, cost per question and safety. An agent that can read untrusted content, see private data and act externally needs strict limits on at least one of those three.
